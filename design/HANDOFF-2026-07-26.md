## Hosts can pull now — FIXED 2026-07-27

Superseded. This section used to read "no host can `git pull`", and that was the
single most misleading fact in this document. It is fixed on `gpufab-ops-01` and
`gpufab-fabric-01`, and **not yet applied to s3/s4** (see below).

Mechanism: **read-only GitHub deploy keys**, one per repo, in Secret Manager as
`gpufab-deploy-key-{platform,network,docs}`, readable by the compute service
account already attached to every host. `deploy/00-bootstrap.sh` fetches them,
writes `/root/.ssh/config` with a `github-<repo>` alias per key, points each
remote at its alias, and then forces the checkout to `origin/main`.

Deploy keys rather than a token, deliberately: a PAT reaches every repo the
owner can see, read **and** write. A deploy key reaches one repo, read-only, and
is revocable per repo. GitHub rejects the same key on two repos, hence three.

Two things that are easy to get wrong here, because both were:

* **Authenticating is not the property.** Keys and ssh config landed correctly
  while the remotes were never rewritten (the error was swallowed by
  `2>/dev/null || true`) and every fetch still went to https and failed.
* **Fetching is not the property either.** `pull --ff-only` then refused to
  advance over 34 locally-modified files on ops-01 — content that already
  matched `main`, left "modified" by years of tar+scp. Bootstrap now forces
  tracked files to origin and leaves untracked ones alone, because the rendered
  configs, clab topology and venvs live untracked inside those same trees.
  `GPUFAB_NO_RESET=1` opts a host out.

So the assertion is the **end state**, not the mechanism:
`tests/t19-host-can-pull.sh --hosts a,b` — remote on ssh, fetch succeeds, zero
commits behind `origin/main`, zero modified tracked files. It is wired into
`verify.sh` as the `host-pull` phase. Verified 18/18 on both hosts, and verified
to FAIL on a nonexistent host rather than pass on zero observations.

A token is still needed for GitOps **PRs and the relay** — deploy keys are
read-only by design — so the `gpufab-gh-token` warning at the end of bootstrap
is accurate and should stay.

**Still to do:** s3 and s4 have not been seeded, because a force-checkout would
have swapped code underneath the recovery agent that was live on them. Seed each
once by running `deploy/00-bootstrap.sh` there; after that they self-update.
Until then, host-side `git status` remains meaningless on those four hosts and
only `tests/t01-provenance.sh` (workstation-side checksums) is trustworthy.

## sim 2 is degraded, and it was self-inflicted

An automatic rebuild triggered on an ambiguous signal (BGP below threshold while
the fabric was still converging) and reached `containerlab destroy` on a live
124-node fabric. Stage 98 no longer does this — it acts only on the unambiguous
case, a preempted host booting with zero containers, and otherwise reports and
exits non-zero. sim 2's state is a consequence of that mistake, not a
pre-existing fault. Treat **s3 as the reference sim**.

## What was fixed today (all committed and pushed)

- **Bulk seeder**, then parallel bulk POSTs: ~5/sec → **8.31 cables/sec**
  (82/sec in the post-sync test). Root cause of the original slowness was NOT
  the seeder — the `/fabric` service was starving it by re-serializing the whole
  topology on every request, its cache invalidated by the seed's own writes.
- **`/fabric`**: 600s timeout → **15.9s build, 43ms serve**. Cause was NetBox's
  generic-relation serializers on cables, plus `connected_endpoints` tracing the
  cable path per interface (19.7 ms/record vs 4.2 brief vs 2.2 uncabled). Found
  with py-spy, not by reasoning.
- **Spot restart proven**: `TERMINATED → RUNNING` in 90s, unattended.
- **`t11-config-applied.sh`**: asserts rendered config actually reaches the
  switch — the handover no stage was checking, and where switch BGP was lost.
- **`gpufab.py topology` deleted**: reported 30 switches for a 48-switch profile
  and was feeding the deploy's health gate.
- Numerous "reported success while measuring nothing" fixes: `|| true` on the
  apply step, `wait_healthy` using string equality, `t_zero` passing on empty
  input, a recovery path that ran zero stages and printed "complete".

## The recurring failure mode

Nearly every bug found today had one shape: **a check that reported success
having measured nothing**, or measured the wrong thing. The countermeasures are
`tests/lib.sh` (assertions take an observed count; zero observations is a
failure), `expected.py` (one derivation of what should exist), and `t11`
(compare against the device, not against a metric). Prefer those over improvised
verification — see the `feedback-script-not-adhoc` memory.
