### #58 (O4) — closed by a diff, not a fourth hypothesis

**Root cause.** ZTP writes `config_db.json` and nothing else — the whole ZTP
descriptor was one section (`render_fabric_ztp.ztp_json()` pre-`a2fafb1`), so
`/etc/sonic/snmp.yml` kept the image default `public`. `docker-snmp` is a
**`delayed`** container: it starts ~45s after the ZTP config lands, runs
`/usr/bin/snmp_yml_to_configdb.py`, and that script ADDS every community named
in `snmp.yml` that is not already a key — putting `SNMP_COMMUNITY|public` back
underneath a config that had just been declared correct.

**Measured on a real leaf**, and this is the one number of the round with a
committed evidence artefact
(`evidence/2026-07-28-o4-cold-insync/fixed-run-timeline.txt`, 20s poll
granularity, one leaf, twice — the file is confusingly named and contains BOTH
runs):

```
07:57:51  tables=28  SNMP_COMMUNITY=['258426a9…']
07:58:14  tables=28  SNMP_COMMUNITY=['258426a9…']
07:58:35  tables=28  SNMP_COMMUNITY=['258426a9…','public']
```

**44 seconds, against a 90s settle.** The window was never narrow; it was wide
open and nothing was looking.

**The fix is a `00-snmp` ZTP section, not a longer wait** (network `a2fafb1`).
ZTP runs sections in `sorted()` order and picks the plugin by stripping a
leading `^[0-9]+-`, so `00-snmp` reaches **the image's own
`/usr/lib/ztp/plugins/snmp`** and writes `snmp.yml` correctly *before* the
config lands. `restart-agent: False`, deliberately — the `01-configdb-json`
section reloads everything moments later. **No window, rather than a narrower
race.**

**Why `auth_tables` and O11 both verified clean, and this is the lesson.**
`apply_snmp_yml()` writes the correct file only during a push, and it does not
remove what the container already wrote. It makes run **N+1** clean and can
never make run **N** clean. Every warm measurement was reading the result of the
previous run.

Three hypotheses died on O4 — `auth_tables`, then SNMP suppression, then O11 —
each confirmed against a running fabric and each false cold. What finally worked
was the field-by-field diff this document had already prescribed. That diff is
now committed as `tests/probes/insync_live_diff.py`, salvaged in `1e33778` from
a branch cut ~70 commits behind `main` and deleted; `feature_rewrite_probe.py`
and `ztp_state_capture.py` came with it. **Rebuilding that tooling next time is
the waste that commit prevents.**

### #92 (O38) — bootstrap and steady state are different phases

**Phase is a function of existing records, not a flag** —
`tools/interim_deploy.py:1190`:

```python
steady = bool(art_tables and box_tables and declared)
```

`DROP_TABLES` became a **conditional floor**, and `- owned` now applies to it
(`interim_deploy.py:1202-1204`):

```python
floor = set() if steady else set(DROP_TABLES)
strip = set(_REWRITE_FROM_INTENT) | (
    (floor | declared | removed) - set(owned) - set(_NEVER_REMOVE))
```

**A table this render wrote cannot also be factory cruft** — which is what makes
`VLAN` (in `DROP_TABLES`) adoptable.

**The brief for this work asserted that a peerless device is just a
previously-owned-now-not case the manifest already handles. That was FALSE, and
the agent proved it rather than implementing it.** `BGP_NEIGHBOR` is in
`_LEGACY_OWNED_WRITE` (`interim_deploy.py:934`), so it is in `owned`
unconditionally, and the strip subtracts `owned`. Dropping the floor would have
left **every peerless device inheriting stale neighbours**. Keep the floor.

The write site was fixed too — no-peers is now an **opinion**, not an omission
(`interim_deploy.py:706-709`):

```python
if nbr:
    cfg["BGP_NEIGHBOR"] = nbr
else:
    cfg.pop("BGP_NEIGHBOR", None)
```

The table is *removed* from the grafted config rather than left alone. Commit:
network `199664b`; test `t36` (`258f74d`), run against pinned pre-fix code.

r = run_ssh(ip, f"sudo cp /tmp/gpufab_owned.json {BOX_MANIFEST} && "

Both halves are in network `18f5d4e`, along with a single decision point

### #126 — the anycast gateway was not anycast

Three MACs answering one gateway address, so **leaf02 and leaf03 hairpinned
gateway traffic over VXLAN to leaf01**. The fabric was converged, every session
was up, and the traffic was taking a tunnel to reach its own default gateway.

**SONiC native SAG is not supported on this image** — no `sonic-sag.yang`, no
`SagOrch`; VRRP is a CLI with no daemon behind it. The fix is
`VLAN_INTERFACE.mac_addr`, i.e. give all three VTEPs the same gateway MAC.

**The MAC alone was insufficient, and that is the part worth keeping.**
`advertise-default-gw` had to come off as well — with the MAC unified but the
advertisement left on, the fabric still hairpins, **just with a tidier MAC
table**. A fix that makes the symptom harder to see is the most expensive kind
here.

**The wave unit had to be all three VTEPs at once**, and this is a #99 finding
with teeth: a partial anycast-gateway state is not degraded, it is
**incoherent** — some leaves answering locally and some tunnelling, with no
consistent story about where the gateway is. **A release mechanism must know,
per feature, whether a partial rollout is SAFE, DEGRADED or INCOHERENT.** #99
currently has no code; this is the requirement it has to satisfy.

### #128 — the render fingerprint could not see the feature modules

**Confirmed live, and this is the cleanest demonstration of the class:** the
#117 render **changed output on two devices** while `manifest.json` came out
**byte-identical on all 48**. The fingerprint that exists to say "the render
moved" did not move.

Cause: the import closure starts at `render_fabric_ztp.py`, which does
`import features` at module scope, and `_resolve()` maps that to
`features/__init__.py` **only**. The modules that actually render the feature
never entered the set.

**The fix follows the package directory, not a list of files** — on resolving
any `__init__.py`, every `*.py` under it is `rglob`ed and **queued back into the
same worklist**, so each member is then AST-parsed and its own imports join the
closure too (`render_revision.py:210`, `:272-273`). Bounded by `_resolve`'s two
search roots, so it cannot wander into site-packages.

> **The reason a "just add the import" fix would have failed is real, but the
> claim usually made about it is wrong.** It is *not* true that both natural
> spellings contribute nothing. `from features import evpn` **does** contribute
> — it records the package and pulls in `features/__init__.py`, exactly as
> `import features` already did. What it never does is reach `evpn.py`. Only
> `from . import evpn` contributes literally nothing, because `ast.ImportFrom`
> with `level>0` has `module=None` and `_module_scope_imports` appends only a
> truthy `node.module` (`render_revision.py:181-185`). The distinction matters:
> the failure is "resolves to the package, not the module", not "resolves to
> nothing".

**#133 says the blind spot is still wider than #128 closed it.** The fingerprint
now watches `features/*.py`, but not `gpufab-network/tools/seed.py` (a
function-scope import on a render path), not the 15 `design/profiles/*.yaml`
that decide TACACS/ZTP/gateway addresses and the whole `features:` block, and
not `/opt/gpufab/secrets/{tacacs_key,snmp_secret}`. All of them change artifacts
without moving the fingerprint.

### O11 SNMP — DONE, merged (§5.11)

Root cause was `docker-snmp`'s `snmp_yml_to_configdb.py` rewriting

|---|---|---|

## Traps a fresh reader will hit

- **`gpufab-platform`'s local `main` branch is STALE, and the checkout is not on
  it.** The working tree sits on branch **`o5-merge` at `dc9a05d`, which is
  exactly `origin/main`**; local `main` has moved on from `ae3bc4e` to `8d4c7ff`
  and is now **32 commits behind** — the number changes every session, the trap
  does not. `git checkout main` in that repo silently moves you into the past,
  across the O4 fix, the manifest work, the convergence gate, routed OOB, the
  EVPN module and the render fingerprint — every one of which fails quietly
  rather than loudly. Check `git rev-parse --abbrev-ref HEAD` and
  `git rev-list --count main..HEAD` before believing anything you read there.
  `gpufab-network` and `gpufab-docs` are both on `main` and both equal
  `origin/main`.
- **`grep -q` in a pipeline is a SIGPIPE trap under `pipefail`.** `grep -q`
  exits at the first match and closes the pipe; the writer upstream takes
  SIGPIPE and exits 141; `set -o pipefail` makes 141 the pipeline's status. The
  head's DHCP liveness check did exactly this and so **failed BECAUSE the server
  was busy** — it passed on a quiet server whose log was four lines long, and
  failed the whole head role once the log reached 6475 lines because switches
  were actually DHCPing (`a76263d`). Measured on the same container: string
  present, shipped condition → 141/FATAL, `set +o pipefail` → 0. Capture the log
  once into a variable and count with `grep -c`, which reads to EOF. **This is
  the third time this one check has been wrong and the third time in the same
  direction — failing closed on a healthy server.**
- **`pgrep -f <pattern>` matches its own command line.** This killed an agent's
  own shell EIGHT times in this project, twice in one evening by me. Use exact
  pids or bracketed patterns by default.
- **`grep -c` prints 0 AND exits 1.** Under `set -e`/`pipefail` that aborts
  silently; `|| echo 0` fires on the SUCCESS path and yields the two-line string
  `"0\n0"`. Seven separate failures, including inside tests written to catch it.
  Prefer `wc -l`.
- **§5.10 is the architectural frame**: git holds design intent (the cabling
  plan), NetBox is the operational record. Booting the fabric from the profile is
  MORE faithful to real ops, not less — nobody waits for DCIM before cabling.
- **The reconciliation trap.** An early `--from-profile` supplied positional
  interface names instead of assigned ones; `port_index()` would have turned
  those into wrong port numbers and MISWIRED the fabric, with every layer
  internally consistent. That is the 32-port-PORT-table signature that cost 178
  BGP sessions. A profile-hash check compares intent to intent and would NOT have
  caught it; reconciling booted topology against NetBox would.
- **Cold reset**: use `terraform apply -replace` on the instances, not
  `99-teardown.sh`. Fresh-by-image cannot have the bug class teardown scripts have
  — and teardown demonstrated exactly that bug class this session.
- **Multi-tenancy** (§5.8) is service separation, not a security boundary. Read
  it before claiming isolation; several of its items remain open.
- **A positive control that can never fire is worse than none.** `image-scrub.sh`
  planted its credential decoy at `/root/.gpufab-scrub-probe-id_rsa` and hunted
  with `-name 'id_rsa*'`, which anchors at the START of the basename — so the
  control never matched. Its verification block runs LAST, so every scrub did all
  its removals and then died on check one, and an image was captured from a host
  whose proof never ran (#74). The fix was to rename the decoy to exactly what the
  sweep looks for; widening the sweep to `*id_rsa*` to make the control pass would
  have weakened the very thing under test.
- **Cloud-init does NOT regenerate SSH host keys on the same instance.** The scrub
  script's comment said it did. A stop/start after a scrub left port 22 dead and
  recovery needed an out-of-band `ssh-keygen -A`. Fresh instances launched from
  the image are fine; the scrubbed host itself is not.
- **A non-fatal component can silently un-gate a good build.** `70-telemetry`
  losing a first-boot D-Bus race took six of seven gate phases with it, on a
  fabric that was in fact converged 1464/1464. This is the INVERSE of the usual

## Fabric verification redesigned: reachability matrix + continuous watch (2026-08-01)

Platform `0be34e9` (t56/t57), `56db947` (stage 58). #137 closed as **wrongly
premised by me**; #138, #139 filed.

### The instrument was wrong, and changing it found real defects immediately

`t56` infers forwarding from per-switch counter deltas. On a healthy fabric that
returns *"33 forwarding, 11 quiet, 2 stopped"* — weak, and unattributable: it
cannot say which node cannot reach which node.

`t57` is a **reachability matrix**: 8,184 probes in **11 seconds**, every failure
naming an exact ordered pair. It found **594 unreachable pairs on its first run**
(#139). The clearest case:

    fr-leaf01 Loopback0            10.0.4.36/32
    show ip bgp 10.0.4.36/32       Paths: (2 available, best #1)
    host: ping 10.0.4.36           UNREACHABLE
    host: ip route get 10.0.4.36   via 172.20.0.1 dev eth0   <- the DEFAULT route
    host: routes to 10.0.4.x       0

Control plane perfect, no route on the host, probe leaves over the management
bridge. **The #109 shape, and no counter-delta check could have named it.**

### #137 was mine and it was wrong

I filed it suspecting the backend rails could not forward. They forward fine —
the hosts hold **14,199 BGP routes** with ECMP across the rails (`10.0.0.1` via
`rail1p1`…`rail7p1`; 593 routes each on `rail7p1/7p2/8p1/8p2`). `--bind-dev`
failing was a **local kernel artifact**: forcing `oif` makes the kernel treat the
destination as on-link and ARP for a host not on that /31. Nothing left the box.
The real fault was target selection in the generator — that one host pair happens
to resolve over storage and frontend.

### Two calibration defects in my own test, both refuted by the fabric

- **`DUR=20` read the same exporter poll twice** and reported 43 switches not
  forwarding on a healthy fabric. The poll cycle is ~61s (updates at
  t=15,30,76,91,137). A window that captures no poll is now a *failed
  measurement*, not a fabric verdict — the two are indistinguishable by deltas
  alone, and only one is about the fabric.
- **`MULT=3` was unreachable at any safe rate.** Measured: a backend leaf moves
  1779 → 2158, i.e. 1.21×; 3× would need ~1.28 Gbit/s aggregate on
  software-dataplane VMs. 1.15 is a gross-failure detector and says so.

### The isolation question, and what it turned up

Asked whether a userland compute node should reach the OOB fabric. It should not
— traffic from a compute node through OOB is an **isolation failure, not
coverage**, and my first t56 comment had that backwards.

Measuring it produced **#138**: the substrate is correctly blocked (0 of 66 hosts
reach `10.10.0.48`), but every host's `eth0` sits on the **same management bridge
as every switch**. A GPU node can ping all switch management IPs and
`wget http://172.20.0.4/<device>/config_db.json` — retrieving `SNMP_COMMUNITY`,
`TACPLUS`, `TACPLUS_SERVER`, `AAA` — and enumerate all **122 devices**.

### Continuous, and why this one gets a timer

`deploy/58-fabric-watch.sh` runs the matrix every 10 minutes and publishes
`gpufab_reach_unreachable` / `gpufab_isolation_breach`. **Stage 56 has no timer
because it WRITES BGP config; t57 sends ICMP and reads counters.** Read-only
versus write is the whole distinction, and it is why one is safe unattended.

A run that parsed nothing publishes a **failure marker rather than zeros** —
"0 unreachable" is exactly what a healthy fabric looks like, and that inversion is
the defect this project keeps producing.

## The isolation architecture is bigger than the sim models it (2026-08-01)

Clarified during the fabric-verification work, and it reframes #138 from a bug
into a symptom. The intended design has **two OOB fabrics** and **two access
tiers**:

    1. OOB MASTER        manages the network fabric — switch SSH, TACACS, SNMP
    2. OOB PROVISIONING  delivers images/data for HOST OS setup
    3. GPU HOST          may reach every fabric it is connected to
    4. GPU USER          may reach only non-OOB fabrics, isolated from tenants

Measured against `fabric_model`:

    fabrics derived:                    backend 36, frontend 5, storage 5, oob 2
    profile keys for a second oob role: NONE
    keys for tenant|vrf|user|isolation: NONE
    a host attaches to:                 backend, frontend, oob, storage

**One OOB doing both jobs**, and **no host/user tier or tenancy at all**.

### Why that ordering of findings matters

I filed #138 as "a GPU node can reach switch management, and can fetch any
switch's ZTP artifact including SNMP and TACACS tables". That measurement stands.
But the framing was wrong: it is not a filtering oversight, it is that **roles 1
and 2 share a fabric**, so a node attached for provisioning — which is correct
and necessary — lands on the same L2 as switch management **by construction**.
No ACL on this topology can separate them.

And role 4 is not unenforced, it is **unrepresentable**: with no user-versus-host
distinction and no second tenant, "isolated from other tenants" has nothing to
test against. One tenant cannot demonstrate isolation.

Filed as **#140** — but see the correction below: my first proposal there was
wrong, and #138 kept as the measured consequence.

### The rule this produced, which is worth keeping

`t57` now states which of the four roles it can assert and which it cannot, and
why. **An assertion about a boundary the topology does not contain is theatre** —
it would either fail forever or pass vacuously, and both teach the reader to stop
believing the suite. So host-to-OOB stays a REPORT until #140 splits the fabric,
at which point it becomes an ASSERT and roles 1/2 become testable.

That is the same discipline as the frozen-counter registry: refuse to publish a
verdict you did not measure, rather than publish a plausible one.

checking whether a check can go red before trusting that it passed.

## Measurability gap closed: requirement 1 is now asserted (2026-08-01)

Platform `ac74e90`.

The worst state a test can be in is asserting something nobody has verified is
correct. t57 asserted that every host reaches every switch loopback — including
the **OOB** switches — and I had recorded requirement 1 as "not assertable".
Both were wrong, and one measurement settled it:

    10.0.0.x  backend   REACHABLE   via st1   learned by the host
    10.0.8.x  storage   REACHABLE   via st0   learned by the host
    10.0.4.x  frontend  unreachable via eth0  NOT learned    <- INCONSISTENT
    10.0.12.x oob       unreachable via eth0  NOT learned    <- CORRECT

**The asymmetry is the proof.** If hosts were not meant to reach switch
loopbacks, backend and storage would not be reachable either. They are, on two of
three data fabrics — so the frontend gap is a defect and the OOB gap is
requirement 1 holding.

### What I had conflated

"OOB strictly isolated from any compute or storage node" is **true on the routed
plane and false on the management bridge**, and I had treated them as one claim.
The OOB switch loopbacks are genuinely not advertised to hosts; the shared
`172.20.0.0/24` bridge is a separate defect (#138). Separating them turned an
"unassertable" requirement into an asserted one:

    OOB isolation probes attempted: 132     <- anti-vacuous floor
    compute/storage reaching an OOB loopback: none
    substrate isolation: none

### And the defect count became precise

594 → **462**. The 132 difference was the OOB column being counted as failure
when it was correct behaviour. Every one of the remaining 462 pairs *should* be
reachable: `fr-leaf01` advertises **0** routes to its host peer while `bk-leaf01`
carries 111 `10.0.0.x` prefixes.

### The rule this reinforces

A test that might be over-asserting is worse than no test, because it teaches the
reader to discount red. The fix was not to weaken the assertion — it was to
**measure which expectation was correct** and then assert both directions: the
reachable set positively, the isolated set inverted, each with its own
anti-vacuous floor so a silently-shrinking target list cannot read as success.

## EVPN is durable as CONFIG, not as FUNCTION (2026-08-02)

Platform `06a0a0f`, issue **#141**. Fabric restored and verified: t03 16/0,
t39 65/0, t50 82/0, **16/16 exchanging**, exporter agrees at 16, underlay 1464.

Found while repairing my own damage from the #139 investigation, and it qualifies
what #127 closed.

### The measurement

A bare `systemctl restart bgp` on a split-unified speaker:

    after restart:  AF present, 3 sessions Established, 0 peers EXCHANGING
    the two spines: silently dropped 3 -> 2 exchanging each
    fabric total:   10/16

The stanza came back from disk exactly as split-unified promises. The underlay
came back fully. **The overlay carried no routes.**

### Four checks called that healthy

    t50 A2          a durable CARRIER exists (mode + frr.conf on disk)  -> PASS
    t03             counts state == Established                         -> 16/16
    56 --check      evpn_est counts state == Established                -> 3
    56 --reconcile  skipped: "AF present — no action"

Only `gpufab_bgp_evpn_peer_up` — requiring `pfxRcd > 0 or pfxSnt > 0`, the #118
criterion — reported 11, then 10. **The exporter was right and four checks were
wrong**, for the second time in two days.

### What it means for #127

The address family *does* survive; that claim stands. What was never asserted is
that sessions RESUME EXCHANGING. So split-unified delivers **configuration
durability, not functional durability** — and the `--probe` runs that verified
#127 used the naive `state == Established` count, so they reported `DURABLE` on
devices that may not have been exchanging. That verification was weaker than its
wording.

### Fixed, and deliberately not fixed

`--reconcile` now keys on prefixes moving rather than stanza presence, and
repaired 10/16 → 16/16. An exchange count that cannot be read is not acted on.

The naive count still appears in `t03`, `56 --check`, `t50` A2 and `--probe`.
Widening all four is probably correct — a session exchanging nothing is not a
working session — but it would change what several currently-green checks mean
and turn some red. **That is a deliberate tightening, not something to fold into
a repair**, so it is filed as #141 rather than done quietly.

### The pattern, stated once more because it keeps paying

Every time this project has been surprised, the surprise was one layer beneath
the thing being measured. Sessions established / routes installed / config
present are each true and each insufficient. The only checks that have caught
real defects are the ones that measured the NEXT layer down: prefixes moving,
FIB content, the peer's view, bytes on the wire.

## #139 fixed in the renderer, lab-confirmed, NOT yet rolled out (2026-08-03)

network `c5425ae`, platform `9d974ef`. Issue **#139** (loopback /32s never reach
the hosts) has a landed code fix and a lab proof. It is **still open** because
production is still unreachable: this fixed only the render, not the running
switches. See "What is NOT done" below before assuming the pairs are closed.

### Root cause (one layer beneath, again)

Under `docker_routing_config_mode=split-unified` (the #127 durability fix) the
switches carry `bgp suppress-fib-pending`, which withholds a route from BGP
advertisement until BGP has installed it in the FIB. The renderer originated the
switch loopback /32 via `redistribute connected` (route-map clause
`permit 10 / match interface Loopback0`). But the loopback's **connected** route
already owns that /32 in the FIB at admin distance 0, so the redistributed BGP
copy (distance 20) is FIB-pending **forever** and is never advertised — and its
presence shadowed the correct `network <loopback>/32` origination that was also
in the config. Every split-unified speaker's loopback reached no peer; the hosts
route to those loopbacks, so 594/8,184 pairs were unreachable.

This is the #127 fix and the #139 bug being the same line of config: turning on
split-unified is what activated suppress-fib-pending, which is what made the
redistribute path a black hole. A win one layer up opened a hole one layer down.

### The fix (one code line)

`frr_render.py`: flip the route-map clause matching Loopback0 from `permit 10`
to `deny 10`. The loopback is then excluded from `redistribute connected` and
originated **only** by `network <loopback>/32` (already present, line 242), which
advertises correctly with suppress-fib-pending on — because a `network` route
advertises on RIB presence, not on installing a BGP copy. This is how bgpcfgd
originates the loopback in separated mode. `suppress-fib-pending` is left ON;
non-loopback connected routes are unchanged (clause 20 still permits them).

The two check mirrors (`c6` gen_frr_conf, `c7` gen_frr) carried the same
`permit 10` and were fixed identically, so they validate the corrected render
instead of the bug. c6's `verify_artifact_shape` token moved to `deny 10` too.

### The lab proof (c6 M5, the assertion whose absence let this ship)

c6 ran the fixed `gen_frr_conf` in an isolated 2-node SONiC-VS lab on
`gpufab-s11-fabric`, and M5 (loopback advertisement) scored **green at every
phase**:

    m5_inbgp   (prefix in own BGP table)          baseline=1 switched=1 restart#2=1
    m5_notadv  (FRR says NOT advertised; 1=defect) baseline=0 switched=0 restart#2=0
    m5_peerhas (PEER holds the prefix — end-to-end)baseline=1 switched=1 restart#2=1

Verdict: `SPLIT-UNIFIED HOLDS THE AF AND ZEBRA IS INTACT -> adopt as-is`, with
`M5_FAILED` unset, suppress-fib-pending on, and the default-mode negative control
still reproducing #135 (AF absent after restart). Live fabric untouched: 124
containers before and after; the c6 lab (`c6evpndur`, 172.30.0.0/24) self-cleaned.

The check earned this only because M5 was ADDED first (2026-08-01). The prior c6
compared rendered-vs-applied config and never asked whether the peer receives the
loopback — the exact "measured nothing" shape this project keeps paying for.

### What is NOT done — production is still unreachable

- The **served ZTP tree** still holds the OLD `permit 10` render (c6 flagged this
  as a non-fatal shape warning: `/opt/gpufab/ztp-srv/.../frr.conf` is still the
  old artifact). The renderer fix must be **published** to the ZTP tree.

- **#141** (widen the naive `state==Established` checks to prefixes-moving in t03,

Rollout plan, when approved: publish the corrected render to the ZTP tree

## #142 was a t57 ORACLE defect, not a reachability gap (2026-08-05)
