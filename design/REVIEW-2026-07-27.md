## 1. How the pieces run: sequence and ordering

Today produced a lot of individual tools and stages. This section says how they
chain.

### 1.1 The deploy sequence

`deploy/deploy.sh` is the single audited entry point. It runs numbered stages,
and **the order of the `STAGES` array is authoritative, not the numeric names.**
The file says so explicitly (`deploy.sh:61`):

> (Numeric stage names no longer match array order — the array order is
> authoritative.)

There are two lists, deliberately kept separate, and a stage must appear in
**both** or it silently never runs:

- `STAGE_ROLES` in `tools/fabric_model.py` — **membership**, i.e. which role owns
  a stage. `fabric_model.py --stages head|fabric` prints it. Single definition.
- `STAGES` in `deploy/deploy.sh` — **order**. Order is a deploy concern
  (observability before fabric); membership is a model concern.

Declared order (`deploy.sh:67`):

```
00-bootstrap  10-images  20-services  30-seed  70-telemetry  80-portal
85-console  40-topology  45-isolation  $CONFIG_STAGE  60-auth
90-automation  95-logship  97-fleet-watchdog  98-spot-rebuild
```

`$CONFIG_STAGE` resolves from `USE_ZTP`, which defaults to `1`:
`USE_ZTP=1` → `50-ztp-provision` (the product path, blank boot + DHCP opt67);
`USE_ZTP=0` → `50-configure` (interim config push).

Filtered by role, the actual sequences are:

| `ROLE=head` (ops host) | `ROLE=fabric` |
|---|---|
| `00-bootstrap` | `00-bootstrap` |
| `20-services` (NetBox = SoT) | `10-images` |
| `30-seed` | `70-telemetry` |
| `70-telemetry` | `40-topology` |
| `80-portal` | `45-isolation` |
| `85-console` | `50-ztp-provision` *(or `50-configure`)* |
| `90-automation` | `60-auth` |
| `95-logship` | `95-logship` |
| `97-fleet-watchdog` | `98-spot-rebuild` |

`55-unnumbered` is in `STAGE_ROLES` (fabric) but **deliberately not in the
`STAGES` array** — commit `474eb94` calls it "opt-in, and destructive". It is
reached only by `--only 55`.

**Entry points, and how they differ:**

| invocation | what it runs |
|---|---|
| `deploy.sh` | the whole `STAGES` array, role-filtered |
| `deploy.sh --from 50` | `STAGES` from the first stage matching the prefix |
| `deploy.sh --only 70` | one stage; **prefix match, one argument only** |
| `deploy.sh --recover` | `RECOVER_STAGES`, role-filtered |
| `deploy.sh --reboot` | `STAGES` starting at `20-services`; also flips `USE_ZTP` to `0` and reuses the on-disk `-ztp` image |

`RECOVER_STAGES` (`deploy.sh:71`) is the emulation-state subset:

```
70-telemetry  80-portal  85-console  40-topology  45-isolation
$CONFIG_STAGE  60-auth  90-automation  95-logship
```

97/98 are **not** in `RECOVER_STAGES`: they install the self-heal machinery, and
a recovery triggered *by* that machinery re-installing it is circular
(`c1810f4`).

**The `--reboot` defect fixed today.** `--reboot` begins iterating at
`20-services`, which is a **head** stage and is filtered out of the fabric role.
On a fabric host the loop therefore never started, `deploy.sh` printed
"deploy.sh complete", and stage 98 logged "rebuild COMPLETE" **one second after
starting** — a self-heal unit reporting a successful rebuild of a fabric it had
not touched. `c1810f4` makes both `--reboot` and `--recover` count what they ran
and FAIL on zero, and `--reboot` now names the reason. `--only` had the same
shape and now fails when it matches nothing.

### 1.2 Ordering that is load-bearing

**Observability first — 70-telemetry before 40-topology.** Deliberate, so an
operator can watch switches boot and BGP sessions establish live. The
consequence: on a fresh host the exporter starts with **nothing to scrape**,
exits, and under systemd's default limit of 5 starts in 10s is *permanently
dead* by the time the topology appears five minutes later. Observed on
`gpufab-s3-fabric`: exporter failed 19:15:39 with "Start request repeated too
quickly", topology deployed ~19:20, and the host reported **BGP=0/0 for an
hour** — which reads as an unconverged fabric and was a dead collector.
`776b0dc` sets `StartLimitIntervalSec=0` with `RestartSec=15`: retry forever,
slowly, until the fabric exists.

**97/98 run LAST.** Both install self-heal machinery. Arming a rebuild unit
before the fabric exists points it at an empty host — and 98 in particular
triggers on "is the fabric empty?", so arming it mid-deploy would let it fire
against a fabric that is merely unfinished (`1e1fcd5`).

**Inside 50-ztp-provision, render precedes apply.** The stage runs, in order:
TACACS/secrets assert → start the OOB ZTP server (renders from NetBox, serves on
`172.20.0.4`) → wait for DHCP leases → **config-push backfill via
`interim_deploy.py`** → read `BGP_NEIGHBOR` back off a sample of switches. The
render must precede the apply or the apply pushes stale config. The backfill's
exit status was being discarded by `|| true` — see §5.

**`deploy/lib.sh` is SOURCED by every stage**, so anything it does at *source
time* happens on *every stage run*. That is exactly how `/opt/gpufab/profile`
came to be rewritten to `lite.yaml` by unrelated stages:

```
PROFILE="${PROFILE:-$NETWORK/design/profiles/lite.yaml}"
echo "$PROFILE" | sudo tee /opt/gpufab/profile >/dev/null 2>&1 || true
```

Measured across the fleet on 2026-07-27: **four of six hosts had been relabelled
this way, two of them within the preceding half hour**, while running 124-node
S1 fabrics. `cb873d8` splits this into *resolve* in `lib.sh` (caller's `PROFILE`
wins, else what this host last recorded, else the lite fallback which is **never
written back**) and *record* from `deploy.sh` after dispatch. Full detail in §5.

**Other ordering that matters:**

- **60-auth after 50.** AAA/TACPLUS tables are pushed by stage 50; 60 re-asserts
  the TACACS server and rotates the local password. A freshly rebuilt switch is
  at the factory password until 60-auth has run — which is why a healthy switch
  can answer ssh with `rc=5 Permission denied` mid-rebuild.
- **45-isolation after 40-topology**, because the DOCKER-USER rules it installs
  reference containerlab's bridges, which do not exist until the topology is
  deployed.
- **Within 55-unnumbered, hosts go before switches.** A switch offering
  unnumbered to a host still speaking numbered forms *no session at all*, so a
  half-migrated fabric has a dead link at every boundary. Hosts reconfigure in
  seconds (`docker exec` + daemon restart) while a switch `config reload` takes
  60–90s, so pushing hosts first makes the disagreement window as short as the
  slow side alone (`04e4fa2`). Pushing them as separate passes produced 221, then
  167, then 82 sessions — which reads as progressive breakage and was only ever
  "how many links currently have both ends agreeing".
- **`config_db` and `frr.conf` are pushed before a SINGLE reload.** Reloading
  between them leaves a window where the device has `split-unified` set and no
  `frr.conf` to read — a switch with no BGP configuration at all (`474eb94`).

**Non-fatal stages.** `NONFATAL="60-auth 70-telemetry 80-portal 85-console
90-automation 95-logship"` — a broken auth server must never take down
telemetry. Infra/images/services/seed/topology/configure stay fatal; they are
prerequisites.

### 1.5 Recovery sequence

What happens automatically when a spot fabric host is preempted:

1. GCP preempts the instance. `instance_termination_action = STOP`, so the host
   is left **TERMINATED** — it does not boot, and terraform will not start it
   either, because a stopped instance still matches its configuration exactly.
2. **Stage 97 `gpufab-fleet-watchdog`** (ops host, 2-minute systemd timer) lists
   instances matching `name~fabric`, sees TERMINATED, and starts it. It lives on
   the ops host because a preempted host cannot start itself, and the ops host
   must never be spot.
3. The host boots. `startup.sh` restores Docker; `70-telemetry` restores the
   exporters. **FRR host containers are `restart=always` and come back by
   themselves; the QEMU-backed switches are `restart=no` and do not.** So the
   host returns with Docker healthy, exporters running, dashboards answering and
   **no switches** — which is why stage 98 must compare against the SoT's device
   count and not against zero.
4. **Stage 98 `gpufab-rebuild.service`** (boot unit, fabric host) resolves this
   host's SoT, proves it answers 200 *and* holds devices, compares running
   containers against the SoT's device count, and runs `deploy.sh --recover` if
   short.

Measured on one real drill (`gpufab-s4-fabric`, SPOT, s1-512 — `runbooks/start-stop.md`):

- stage 97 restarted the instance in **17s** unattended (`automaticRestart` is
  false, so GCP did not). A separate observation records **TERMINATED → RUNNING
  in 90s**; the abandoned `sims.tf` edit records **~120s**. These are three
  measurements of the same mechanism, not a contradiction, but the spread is
  worth knowing.
- stage 98 correctly classified a **76-of-124** boot as PARTIAL, reached the
  right SoT, and rebuilt **124 nodes / 1466 links with all 48 VMs healthy in
  ~4 min**.
- **Routing recovery is NOT proven.** The rebuild was still activating at **19
  minutes with 0 BGP sessions** when measurement stopped. Node recovery is
  demonstrated; routing recovery needs a human.
- Two barriers make a healthy rebuilt switch look dead: regenerated containerlab
  host keys (`rc=255`) and the factory password before 60-auth (`rc=5`).

## 2. The model — `fabric_model.py`, addressing, ports, placement

*7 commits in platform, plus 4 profile commits in network.*

This is the largest single body of change today and it does not fit the suggested
buckets, so it gets its own section. Everything downstream — seed, render,
topology, expected counts — derives from here.

**The problem.** Growing `S0 → S1` renumbered **42 of 43 devices** — every
loopback, mgmt IP and ASN. Adding capacity therefore meant reconfiguring the
fabric you already had, which is the opposite of the "+1 pod forever" growth this
architecture claims, and the reason every rung needed a destructive rebuild.

**`e9e5c92` — positional index + declared growth envelope.** Four independent
causes, each of which survived the previous fix because it lived elsewhere:

```
pidx += 1 per device      adding a leaf slid everything after it
next(mh) for mgmt IPs     mgmt slid even once loopbacks were stable
nidx across node classes  adding GPUs moved cpu0001
Plan field widths sized   widths derived from the CURRENT topology, so growth
from the topology         widened the index field 6 -> 7 bits and relocated
                          every address anyway
```

Each category now occupies a block sized by a **declared** maximum, and a
device's index is its position within that block. Exceeding the envelope raises a
named `ModelError` naming the field to widen — an explicit, reviewed renumber
rather than a silent consequence of adding hardware. **Result: `S0 → S1`
renumbers 0 of 43 devices when both declare the same envelope.**

**`3afa4ec` — the envelope must declare pod count.** `max_pods` came from the
*observed* pod count, so adding a pod widened the pod field and relocated every
address inside every pod. `S1 → S2`: **0 of 1465 ports move, 0 of 124 loopbacks,
0 of 124 ASNs.** mgmt still differs deliberately — S2 uses a larger supernet
because two pods need two /24s.

**`29e6a3b` — ports allocate positionally.** The allocator handed out
`used[dev] += 1` in emission order and argued for it ("counters cannot disagree
with emission order because they ARE it"). True, and exactly the defect.
Measured `S0 → S1`: **154 of the 284 shared links changed port**
(`bk-p1-r1-leaf01 → spine01` moved `Ethernet64 → Ethernet256`). Re-seeding then
tries to cable an interface NetBox already has a cable on and dies with
"Duplicate termination found" — **which is why 36 of 64 GPU nodes ended up with
no cables at all.** Each switch now grows two blocks toward each other:
downlinks up from port 0, uplinks down from the last port. Ranking is keyed on
`(peer, Nth link to that peer)` — ranking by peer *name* put the OOB pair's two
parallel links on the same port, a duplicate termination introduced by the fix
for duplicate terminations. **Zero port reuse at S0, S1 and S2.**

  *Honest remainder, recorded not guessed at:* cross-rung port movement drops
  **154 → 128** but is not eliminated. With `leaves_per_rail_plane: 2` a leaf
  serves `gpu0001,0003,0005…` at S1 where it served `gpu0001..0008` at S0, so the
  peer *set* differs and a rank within it cannot be stable. The commit names the
  two design options (index by the peer's global ordinal — stable but sparse, a
  32-GPU leaf reaches port 62 of 64; versus dense packing — compact but only
  stable while the assignment pattern holds) and declines to pick one.

**`c9822ad` — place the core tier from the declared envelope.** The DC core tier
took the pod slot above the *last pod that exists*, so it moved whenever a pod was
added: S3 (5 pods) at block 5, S4 (11 pods) at block 11, **renumbering all 20 core
switches between two rungs declaring an identical envelope.** Inside that block,
each fabric's cores came off one shared iterator, so growing backend cores 16 → 39
slid `fr-core001` from `.18` to `.41` with nothing about the frontend changing.
Measured across the ladder:

```
S0->S1   loopback 0  asn 0  mgmt 0
S1->S2   loopback 0  asn 0  mgmt 48   (deliberate: S2 widens the supernet)
S3->S4   loopback 0  asn 0  mgmt 0    (was 20 renumbered)
S4->S5   loopback 0  asn 0  mgmt 0    (was 4)
```

**`fdd2421` — node NIC ordinals rank within their fabric.** A node names NICs
per-fabric (`fe0`, `st0`), but a GPU node's uplinks are 16 backend rail + 2
frontend + 2 storage + 1 oob, and all landed in one ranked list. The first
frontend NIC was numbered **16** and the model emitted `fe16` for a node that has
`fe0` and `fe1`. `seed.py` looked it up in the device template and died with
`KeyError` **after 16 of 1466 cables**, leaving the SoT full of devices with
almost no links. *That is what "the DGX boxes have no connections" was.*

**`87fc8a1` / `86c8f44` — placement and sharding.** `fabric_model.place()` has
always decided which host each device lands on; `gen_topology.py` ignored it and
emitted one flat topology, which is why `fabric_host_count=2` produced **two
disconnected half-fabrics rather than a fabric**. `--host` now emits one host's
slice: a link with both ends local is an ordinary veth, a link with one end
elsewhere becomes a VXLAN endpoint. Each host generates its own file with no
coordination, so **both the host mapping and the VNI are DERIVED** — the VNI from
a hash of the link's sorted endpoints, so it is identical from either side
regardless of which end a host calls "a" (the same a/b-order trap that made
`sot_revision`'s fingerprint unstable). Placement is never stored in NetBox: it
is a property of the profile, and putting it in the SoT would create a second
authority able to disagree with the model that computed it.

**Profiles (`gpufab-network/design/profiles/scale/`).** `a38928b`, `298d80b`,
`3d9637f` declare growth envelopes: S0/S1/S2 share one (2 pods, 76 nodes),
S3/S4/S5 share a second sized to S5 (35 pods, 136 nodes/pod, 105 backend cores).
**Deliberately a different envelope**, so crossing `S2 → S3` renumbers — adopting
one ladder-wide envelope is a one-time renumber of the S0–S2 family and should be
a reviewed decision, not a side effect of adding a profile. `2199853` fixes S3's
declared backend cores 15 → 16 and S4's 33 → 39; S5 is left broken on purpose
(§13).

**Assessment.** This is the highest-value work of the day and the hardest to
verify by reading. It is backed by `t08-addressing.sh` (20 assertions) which
asserts the *outcome* — devices in both rungs, devices renumbered, devices added
— rather than any one mechanism, "because four separate running counters caused
this and each survived the previous fix".

## 3. The renderer and config derivation

*`render_fabric_ztp.py`, `frr_render.py`, `render_revision.py`,
`vs_port_sets.json`, `switch_catalog.yaml`*

### 3.1 The PORT-table defect — the single most consequential finding of the day

`config_db` held **two tables describing how many ports a device has, from two
different origins.** `INTERFACE` was built from the SoT and was correct at 64
ports on an SN5600. `PORT` was inherited by deep-copying
`vs_base_config_db.json` — **a dump captured from ONE physical Force10-S6000, 32
ports** — so every device in every fabric got that machine's table.

```
config_db INTERFACE   Ethernet128|10.128.9.177/31   rendered, present
config_db PORT        (no Ethernet128)              silently absent
the switch            no such netdev, so no address, so no session
```

Every leaf established exactly 32 sessions while `BGP_NEIGHBOR` correctly held
34–52. **178 of 1464 sessions across three independently built fabrics**, and no
stage reported a problem: the render wrote it, ZTP served it, `config reload`
accepted it, and `t11` compared `BGP_NEIGHBOR` rendered-vs-applied and found them
equal — *they were equal*. On `gpufab-s3-fabric` that was 178 sessions parked in
Active with `never` uptime: 2 on every backend leaf (34 links), 16–20 on every
frontend and storage leaf (48–52 links), and 3 on each storage spine whose
leaf-side port was the missing one.

Fixed in two steps, and the second is the one to accept:

- **`8793c6a` fixed the instance.** PORT comes from a new
  `design/base/vs_port_sets.json` keyed by the HWSKU the device's model asks for,
  and the renderer **raises** rather than emit a config whose interfaces exceed
  it. `Accton-AS7816-64X` is the 64-port table; it is usable because its port
  names are `Ethernet{4*index}` and its `lanemap.ini` is row-aligned with its
  `port_config.ini` — the same property `Force10-S6000` has, so host NIC `eth<k>`
  lands on `Ethernet{4(k-1)}` under both, and widening a running switch adds
  ports 33–64 without renumbering the first 32.
- **`23260dc` closed the class.** PORT is now built from the device's **own SoT
  interfaces — the same list `INTERFACE` is built from — so the two cannot
  disagree about what exists.** The attributes NetBox does not model (lanes,
  speed, index, alias) are joined in from the HWSKU port set *by port name*. The
  catalog becomes the cross-check; the SoT is the origin.

  Everything that can go wrong **raises**, because every alternative reproduces
  the original defect as a config that applies cleanly and is short ports nobody
  counts: a SoT port the HWSKU lacks, a HWSKU with no table, a SoT port the model
  cannot place, two SoT interfaces mapping to one port, no front-panel ports at
  all, and a port count disagreeing with the catalog. **The last is fatal in both
  directions on purpose** — a device whose SoT is *short* still renders something
  internally consistent, which is exactly what a 32-port SoT on a 64-port switch
  looks like.

  Interface classification is an **inclusion** test, not a list of exclusions.
  `eth0`/`bmc0` are mgmt; `Loopback/PortChannel/Vlan/Bridge/Tunnel/Vxlan` and
  NetBox's virtual/lag types are logical; `Ethernet<n>` is a port; anything else
  raises. An exclusion list treats every name it has never seen as a front-panel
  port, so a PortChannel created in the NetBox UI would have become a port that
  does not exist — *the same bug, entered through the front door.*

  Verified against the pre-change renderer on a SoT derived from a profile:
  **s0-64 30/30 and s1-512-small 59/59 devices produce byte-identical
  `config_db` and `frr.conf`.** The only intended difference is `nvidia-sn2201`,
  dropping from 64 PORT entries to the 52 the SoT actually models. **55 of 59
  switches in s1-512-small address more than 32 ports; all are fully backed.**

**Two more inheritances from the same snapshot, found by auditing it.**
`DEVICE_METADATA.mac` survived onto any device with no `primary_ip4`, and every
VS instance ships the same base MAC (`22:3c:85:c1:e4:36`) — **identical
link-locals, which had already cost 82 of 249 sessions once.**
`DEVICE_METADATA.bgp_asn` (65001) survived onto any device the SoT gives no ASN.
Both now refuse or clear rather than inherit.

Also in `23260dc`: `SLUG2MODEL` is derived from the catalog instead of a
hand-written list that held four of five models, so `generic-vs-32` is no longer
unrenderable with "device type is not in the switch catalog" *while sitting in
the switch catalog*. `pynetbox` moved into `main()` and paths resolve from
`__file__`, so **the module is importable on a workstation** — "the reason
nothing ever tested this is that the only place it could run was the place where
a mistake costs a fabric." That is what made `t14` possible.

**Catalog and docs follow-ups.** `ef56238` makes `vs_hwsku` name a HWSKU that
exists (it had named custom SKUs planned for C3 and never built, so every device
silently inherited the 32-port table). `12bdb23`, `a749911`, `c61df56`,
`68ae3f9`, `c7552dc` correct the documentation in `switch_catalog.yaml` and both
READMEs: **the port set supplies a port's ATTRIBUTES, the SoT supplies the port
list.** Under the old reading a HWSKU with more rows than the model was a defect
to be worked around; under the new one it is simply normal, because the surplus
rows are never looked up. Measured after the change, every model renders PORT
equal to its own port count: **sn2201 52, sn5600 64, sn5400 64, as9817-64o 64,
generic-vs-32 32.**

### 3.2 Render provenance — `render_revision.py` (new)

`sot_revision` fingerprints the **input** and cannot, by construction, see a
change in the **transform**. When the PORT table stopped being copied from the
32-port snapshot, *no SoT changed* — so every artifact rendered by the old code
stayed "current" while serving a config claiming hardware the device did not have.

The measurement that proves it (`2e4ce6c`, and recorded in design §4.1.2):
`gpufab-s3-fabric` and `gpufab-s4-fabric` both stamp SoT fingerprint
`5c0d184d7ee65c49` with **124 devices and 1466 cables — byte-identical
provenance — while s3 serves 64-row PORT tables and s4 serves 32-row on all 48
switches.** `sot_revision` correctly reported both current.

`render_revision.describe()` fingerprints the code **and the data** a render
reads, recorded beside the SoT revision in `_provenance.json`. Design choices
worth noting:

- **Content hash, not a git SHA.** Hosts hold no credential; their checkouts are
  frozen at the clone commit with correct `main` content applied by tar, so
  `git rev-parse HEAD` on a host names a commit whose content is not on disk.
- **No list of files.** Code is the transitive module-scope import closure of the
  render entry point; data is whole directories by glob. Both grow by themselves.
- **Absence is data.** A vanished file takes its name out of the hashed material,
  an expected-but-unreadable one contributes `MISSING`, and if nothing resolves
  the fingerprint is `None` rather than the hash of an empty set.

`dfb7127` prints it from `drift.py` alongside the SoT line, in `--json` too.
**Exit status deliberately unchanged** — every artifact rendered before the stamp
existed is UNSTAMPED, and making that exit 2 would turn every fabric red on a
transitional condition.

The content hash proved itself immediately (docs `31840b0`): it caught another
agent's **in-progress, uncommitted** `interim_deploy.py` by content, naming the
one differing file. No commit id could have.

### 3.3 `frr_render.py` — one derivation, two artifacts

Created today (`01805c3`). The rule: **`config_db` and `frr.conf` come from a
single derived intent (`frr_render.device_intent`), never derived twice.** Two
renderers producing "the same" config from one source is how this project shipped
a fabric whose BGP peers sat on subnets that did not exist — and a drift between
these two would be worse, because both land on the *same device*.

It unblocks two things that needed the same thing: **BGP unnumbered** (config_db
cannot express an interface-keyed neighbour at all — `bgpcfgd` drops it silently,
upstream #26960) and **static analysis** (Batfish parses 17 config_db tables and
`BGP_NEIGHBOR` is not one of them; `frr.conf` is where it reads BGP from and is
mandatory). `frr.conf` is written on **both** paths, not only unnumbered.

Details, each from a documented failure:
- `no bgp ebgp-requires-policy` — modern FRR otherwise advertises nothing over
  eBGP until a policy exists, so the fabric comes up Established with zero
  prefixes, *which looks like success*.
- unnumbered interfaces carry **no IPv4 address** — FRR prefers an IPv4 peer
  derived from a leftover /31 over attempting RFC 5549, so the session silently
  forms numbered while the config claims otherwise.
- `neighbor <if> activate` in the v4 address-family — without it the session
  establishes and carries nothing.
- route-map `LOOPBACK-AND-DATA` is now **defined**; an undefined route-map in
  `redistribute` denies everything.
- a peer with no ASN gets its /31 and **no** neighbour — service classes such as
  the Slurm head carry no routing daemon.

Follow-ups: `f2dffde` closes three gaps against c2d's verified recipe
(`ipv6_use_link_local_only`, the `v6only` keyword, dropping the IPv4 /31) — "a
recipe verified once and then re-derived from memory is not a verified recipe".
`33ef642` fixes the p2p-link filter, which required a name starting with
`Ethernet` — true only of switches, so **every host link was silently skipped and
the rendered host `frr.conf` contained zero neighbours** (28 of 249 sessions).
`687eef8` renders host `frr.conf` at all. `58d0709` gives every switch a unique
system MAC derived from its mgmt IP, fixing the shared-base-MAC link-local
collision that cost **82 of 249 sessions**.

`4d4ad0e` / `e689189` move `sot_revision` and `render_fabric_ztp` off
`nb.dcim.cables.all()` — see §6.

## 4. The apply path — `interim_deploy.py`

*4 commits, all overnight. This is the newest work in the review and the least
seen.*

`interim_deploy.py` is **the apply** — the only thing that puts routing config on
a switch. It runs as the config-push backfill inside `50-ztp-provision`.

**`889d23e` — prove the reload landed, and stop laundering the factory PORT
table.** Two defects, both of which let this tool report success over a fabric
that routed nothing. Found while driving `gpufab-s4-fabric` to 1464/1464.

1. **`config reload -y` exiting 0 is not evidence that a config was loaded.** The
   push loop broke on `returncode == 0` and never looked at the box again.
   Measured on s4: **44 of 48 switches sat at factory defaults** — hostname
   `sonic`, `INTERFACE {}`, `BGP_NEIGHBOR {}` — with the correct `config_db.json`
   on their disk, after a push in which **every switch logged `reloaded rc=0
   (attempt 1)`**.

   *The tell was inverted, which is why nothing caught it:* the only four
   switches that came up correctly were the four whose reload had been **rejected
   several times first** and logged attempt 4, 5 and 6. The ones that "succeeded"
   instantly were the ones that had silently done nothing.

   The loop now pushes, reloads, waits for swss, reads the running config, and
   compares it against what was pushed — retrying on **MISMATCH**, not only on
   non-zero exit. **13 of 46 switches needed a second or third attempt, and every
   one of them had exited 0 on the attempt before.**

   The post-condition is the **same predicate** as the skip check, not a second
   one: `already_applied()` delegates to `config_landed()`. "Is a reload needed?"
   and "did the reload work?" are one question, and two implementations would
   drift into disagreeing about a single switch, which is unresolvable from logs.

2. **`build_switch_config()` inherited PORT and hwsku from the running config.**
   The running config is not a source of anything; it is the output of whoever
   wrote the box last — after a blank ZTP boot, the `sonic-vs` image's 32-port
   Force10-S6000 dump. **A run of this tool reverted 24 of 48 switches that had
   just been corrected to the 64-port table, taking 46 BGP sessions down.**
   Nothing reported a problem, because from this function's point of view nothing
   had happened.

   PORT and hwsku are now written from the SoT. Deliberately **not** re-derived
   locally: this tool knows only the device's *cabled* links (34 on a backend
   leaf) while a PORT table must cover every front-panel port it has (64), so a
   locally-built table would be internally consistent, apply cleanly, and be short
   30 ports. `hardware_tables()` calls `render_fabric_ztp.port_table_from_sot()`,
   the same derivation the renderer uses. **Verified on s4: byte-identical to the
   rendered artifact on all 48 switches.** PORT joins `_OWNED_WRITE` and `hwsku`
   joins `_MD_KEYS`, or the skip check would call a switch in-sync while it still
   carried the factory table.

   ```
   a genuine reload           verified on attempt 1, no false failures
   reload stubbed to exit 0   caught on all 3 attempts, FAILED loudly and named
   full 48-switch run         46/46 reloaded+VERIFIED, 0 failed, exit 0, 1464/1464
   t03 / t11 before and after 11 passed 0 failed / 51 passed 0 failed, unchanged
   hardware_tables()          48 switches derived in 0.1s
   ```

**`a5cb3b8` — timing, concurrency, and stop re-reloading switches already in
sync.** This stage is the largest phase of a fabric deploy — **14m00s of a 22m27s
convergence** on `gpufab-s4-fabric` (19:23:59 → 19:37:59) — and nothing recorded
what it spent that on. Four changes, in order of cost:

1. **Unconditional reload.** It ran `config reload -y` on every switch every
   time, including switches that had already self-provisioned correctly via ZTP.
   A reload is ~60–90s of SONiC restarting its whole docker stack.
   `already_applied()` now skips when the tables match; `--force` restores the
   old behaviour. *The snapshot for that comparison must be taken BEFORE
   `build_switch_config`, which mutates the running dict in place* —
   `cfg["DEVICE_METADATA"]` is the same object as `running["DEVICE_METADATA"]`,
   so a comparison made afterwards always matches and the skip fires on switches
   that need work.
2. `max_workers` was hardcoded 6 with a "slirp-friendly" rationale that no longer
   holds — `gen_topology` sets `CLAB_MGMT_PASSTHROUGH`, so mgmt is a real bridge.
3. **Two serial phases nobody counted:** FRR hosts were configured one at a time
   (~76 on s1-512) and `verify()` was a serial loop with a 60s per-switch timeout
   — **48 minutes of worst case tacked onto the end of every deploy.**
4. Per-switch, per-sub-phase timings to `/var/log/gpufab-phases.jsonl`, plus
   `--dry-run`.

**`0ec5d38` — default the push concurrency to the value that was measured.**
Measured on an n2-highmem-64 fabric host, 48 SONiC VS guests, profile s1-512:

```
workers   push phase       waves   per-switch reload
     6      840s (14m00s)      8         105s
    24      297s ( 4m57s)      2         119s
```

**9m03s saved**, and per-switch cost rose **13% at 4x concurrency** — so the
guests are not the limit at 24, which is why scaling is close to linear.

It stops at **24 rather than 48** even though 48 is one wave, and the reasoning
is worth keeping: 48 concurrent reloads pins 48 of the host's 64 vCPUs inside
guests while containerlab and 76 host containers are also running. `55-unnumbered`
already records what that looks like — 30 simultaneous reloads is an I/O storm
that makes slow reloads look like failures. A reload that is merely slow is
indistinguishable from one that failed, the retry budget is 3 attempts, and each
false failure costs a full extra reload. **48 is projected; 24 is measured.** 24
also leaves headroom for the read-back verification that now runs after every
reload. This is a concurrency, not a fraction of the fabric, so a 512-switch
profile becomes 22 waves at the same per-host cost.

**Assessment.** These four commits are the difference between a deploy that
reports success and one that produced a routed fabric. The read-back verification
is the important one; the concurrency default is a measured, reversible
(`GPUFAB_PUSH_WORKERS`, `--workers`) tuning.

### 5.1 Stage 98 — spot rebuild. Eight commits, and the arc is the point.

`98-spot-rebuild.sh` was created today (`87fc8a1`) and then corrected five times,

### 5.2 Stage 97 — fleet watchdog

`8ed7d3f`: the instance filter was `^gpufab-fabric-`, which matches
`gpufab-fabric-01` and **silently misses `gpufab-s3-fabric` and
`gpufab-s4-fabric` — including the SPOT host, the only one that can actually be
preempted.** It would have polled faithfully every two minutes and covered
exactly the hosts that never need it. `tags.items=gpufab-fabric` is the honest
predicate but GCP rejects it as an invalid list filter expression; `name~fabric`
is what the API accepts. Also gives root a `CLOUDSDK_CONFIG` — systemd runs the
watchdog as root, which has no gcloud config and does not inherit the deploy
user's, so the service logged "instance list returned nothing" while the
install-time check, running as the deploy user, reported success. **The install
check now LOGS every host it can see rather than asserting a non-zero count. A
count of one looked healthy and was the bug.**

`f4300a2`: systemd's PATH excludes `/snap/bin`, where Ubuntu's gcloud lives, so
the generated watchdog died with `gcloud: command not found` on every real
invocation. **The install-time checks all passed because they ran as the deploy
user in a login shell — the one context the unit never runs in.** Resolves gcloud
once at install time and bakes the absolute path in; then starts the actual unit
as root and fails the stage if it errors. Also stops merging stderr into the
instance list, where a failed query was being read as a row.

`1e1fcd5`: **97 was registered in `STAGE_ROLES`, listed correctly by
`fabric_model --stages head`, and could not be invoked** — it was absent from
`deploy.sh`'s `STAGES` array, and `--only` reported "matched no stage in this
role", which reads like a typo rather than a missing registration.

### 5.3 `lib.sh` — the profile pointer, and the health gate

**`cb873d8` — resolve the profile, never default-write it.** `/opt/gpufab/profile`
decides what `platform_health` publishes as `gpufab_sim_info{profile=…}`, what
`t13` derives every expected number from, and what `98-spot-rebuild` hands to
`deploy.sh --recover`. **One string, three consumers, two of which are
unattended.** It was assigned *and written* in `lib.sh` at source time (§1.2).

The demonstration is in the commit: `gpufab-s3-fabric`'s pointer was corrected to
`scale/s1-512.yaml` at **00:42:21** by a legitimate stage 98 run. At **00:53:06**
— eleven minutes later, on a fully converged fabric — an unrelated stage clobbered
it back to `lite.yaml`. The SoT value that same stage 98 baked into
`/usr/local/bin/gpufab-rebuild` was untouched, **because only stage 98 writes
it.** *A value written by everything is owned by nothing.*

Resolution order is now: explicit `PROFILE` from the caller → what this host last
recorded → the lite fallback, **which is never written back**. `record_profile`
runs from `deploy.sh` after dispatch, so under `set -e` reaching it is itself
proof the deploy succeeded. Failing instead was considered and rejected: it would
abort 60-auth and 70-telemetry to protect a field they never read. One
consequence: a fresh host deployed without an explicit `PROFILE` now has *no
file* rather than a false `lite` claim; `platform_health` already returns
"unknown".

**`b247ea4` — `wait_healthy` is a threshold, not an identity.** `[ "$h" = "$want" ]`
meant *more* healthy nodes than expected never satisfied the gate. With
`switch_count` stale at 30 against 48 actually-healthy switches, it looped all 45
tries and **failed after 15 minutes on a fabric that had been fully healthy from
the start** — and stage 98's rebuild reported FAILED and stopped before
configuring anything. Two independent defects had to line up: a count that was
wrong, and a comparison that could not tolerate being wrong in the safe
direction.

**`c8659a5` — count switches from the generated topology.** `switch_count()`
asked `gpufab.py`, on the legacy derivation, which answers "switches=30 hosts=7
links=134" for a profile whose real shape is **48/76/1466**. So `40-topology`
waited for 30 of 48 switches, logged "all 30 switch VMs healthy", and proceeded
to configure a fabric with **18 still booting**. Observed live during the S1
rebuild as `healthy=45/30`. It now counts `sonic-vm` entries in
`gpufab.clab.yml`, which `40-topology` writes from the model immediately before
calling this — the gate measures the topology being deployed rather than a second
opinion about it.

**`f7efb29` — `gpufab.py topology` deleted rather than corrected.** It was the
source of that 30/48. "A command that returns a confident wrong number is worse
than a missing one, because nothing prompts you to check it." No callers
remained; each had been moved off it beforehand.

**`ad3f27e` — phase instrumentation and a config-DB probe that can fail.**
`lib.sh` gains `PHASE_BEGIN`/`PHASE_END`, appending one JSON line per phase to
`/var/log/gpufab-phases.jsonl`. And `40-topology`'s config-DB probe was
`for i in $(seq 1 30); … sleep 20` that fell out of the loop and continued
whether or not it observed anything. Three defects, one family:

- **it could not fail, so it was a sleep with extra steps.** Measured on
  `gpufab-s4-fabric`: the **01:03 and 01:22 rebuilds entered this loop and were
  still in it 13m24s and 4m03s later.** With a 15s ConnectTimeout on top of each
  20s sleep the real worst case is **~17 min, not the 600s that `seq 1 30`
  implies**.
- **it probed one hardcoded address, `172.20.0.41`** — a switch in this profile
  by luck, and one switch says nothing about 47.
- 20s polling on a condition that flips in seconds. **A ready switch answers
  `sonic-cfggen` in 4s, measured.**

Now samples three switches spread across the generated topology, polls every 5s,
and FAILs on the deadline (`CONFIG_DB_TIMEOUT`, default 420s).

### 5.4 Stage 50 and the apply handover

**`7ce228b` — the apply step's failure was discarded by `|| true`.**
`interim_deploy.py` is the only thing that puts routing config on a switch, and
it ran as `… || true`. **The stage logged "provisioning stage complete" while
every switch in the fabric held an empty `BGP_NEIGHBOR`. Three fabrics were built
that way** before `t11` compared rendered against applied. The stage now also
reads `BGP_NEIGHBOR` back off a sample and fails if it is empty, **and fails if
it could not sample any switch at all, because a verification that verified
nothing is what got us here.**

**`8ad7116` — the DHCP lease gate compared against `"0\n0"`, not a number.**
`prov=$(… | grep -c "DHCPACK" || echo 0)` — `grep -c` prints `0` **and exits 1**
when it matches nothing, so `|| echo 0` appends a second line. `[ "0\n0" -ge
"$want" ]` is not a comparison, it is an "integer expression expected" error, so
on the first poll the loop's gate errors instead of evaluating. `t13` had already
documented this exact defect and the correct form (`:-`, never a fallback command
that also writes to stdout); it was still live here and in `t11`.

### 5.5 Stage 55 — BGP unnumbered (created today, 8 commits)

`474eb94` creates it: FRR split mode, a rendered `frr.conf` at `/etc/sonic/frr/`,
a location nothing else in the deploy writes to. The bug arc:

- `a082a96`: `cat file | sw_ssh … </dev/null` — **the redirect overrides the
  pipe, so `tee` received an empty stream.** The first run shipped nothing and
  said it was pushing. Same family as the logship bug where ssh consumed the
  device list and 5 of 30 switch logs came back empty — *there `</dev/null` was
  the fix, here it was the bug.* The loop now reads on fd 3.
- `d9e6f12`: the delivery guard ran `wc -c` as the admin user against
  `/etc/sonic/frr`, which the preceding `chown -R 300:300` leaves mode 750. **It
  read 0 on files that had been delivered perfectly and blocked the reload it
  exists to protect.** And the stage declared "unnumbered deploy complete:
  249/249" while every switch still ran the **numbered** config — nothing had
  reloaded and the old sessions were still up. It now proves the **mode** on the
  devices (unnumbered keys neighbours by interface name, numbered by IP).
- `9d28a71`: third instance of the same confusion in one session. **The rule: if
  sudo needs to read or write a file, the FILENAME goes to the privileged
  command — never to a redirect beside it.**
- `fb12b3b`: writing `/etc/frr/frr.conf` changes nothing by itself.
  `frr-reload.py` returned success and applied nothing; SIGHUP does not make
  `bgpd` re-read its config. **The file sat on disk with 20 correct
  interface-keyed neighbours while the running config had none** — this reported
  success twice while the fabric stayed at 221/249. Restart the **daemons**
  (restarting the *container* tears down containerlab's veths).
- `8bdee88` / `04e4fa2`: push to host nodes too, hosts first (§1.2).
- `ab46ca6`: the mode parser grepped `show bgp summary`, **whose column is
  truncated**, so on a wide fabric it matched neither and reported a fully
  converged unnumbered fabric as "STILL NUMBERED". The summary is a human
  display; the JSON is the interface. Also adds the link-local uniqueness
  assertion that the c2d lab check could not make: **a 2-node check cannot
  distinguish "peers by link-local" from "peers with itself" when both ends are
  the same address.**

### 5.6 Bootstrap, auth and firewall

**`e5fbb9e` — never write a zero-byte `gh_token`.** `gcloud secrets … | sudo tee
$SEC/gh_token || true` created an **empty** token file whenever the secret was
unavailable, and continued. Every host then looked provisioned while none could
pull. **`gpufab-s4-ops` sat 2 commits stale behind a 0-byte token and nothing
reported it; `gpufab-ops-01` has no token file at all.** "An absent file is
diagnosable. A zero-byte one is a lie in the shape of a credential."

**`166d375` — the automation private key was mode 0640, so ssh ignored it
fleet-wide.** `chmod 640 $SEC/*` swept up the SSH private key along with the
password files. OpenSSH refuses a private key carrying any group or other bit
when the caller owns it, so **every root-run automation SSH (interim_deploy under
sudo, the bot actions, the reapply path) silently fell back to password auth** —
which then succeeds, so nothing ever reported it. Measured against a live switch
on `gpufab-s4-fabric`:

```
root:ubuntu   0640    as root -> ignored     as ubuntu -> works
root:root     0600    as root -> works       as ubuntu -> cannot read it
ubuntu:ubuntu 0600    as root -> works       as ubuntu -> works
```

`ubuntu`-owned 0600 is the only setting that serves both consumers (the exporter
is `User=ubuntu`, `interim_deploy` is root), because OpenSSH skips the permission
check for a key the caller does not own and root can read it regardless. The
stage now asserts the result rather than assuming it.

**`9d7504c` — fail2ban was banning the automation's own path.** `gcloud compute
ssh --tunnel-through-iap` arrives from `35.235.240.0/20`, and a deploy that opens
many short-lived sessions trips `maxretry 4` **without a single failed
password**. The escalating bantime makes it self-reinforcing, and the fabric
stays healthy throughout, so it presents as a network problem. `ignoreip` now
covers IAP and the VPC; `maxretry` 4 → 6.

**`a561cc0` — stop exposing port 22 to the whole internet.** These hosts took
**~123 brute-force attempts per day**, and it was not merely noise: those
connections occupy sshd's *unauthenticated* slots, so once the queue saturates
legitimate sessions are dropped probabilistically. **It presented as intermittent
IAP flakiness and cost hours of misdirected debugging (fail2ban, MaxStartups, the
network) while the fabric was entirely healthy throughout.** `admin_cidrs` now
allows IAP plus the two workstation addresses **observed in ACCEPTED publickey
logins in the hosts' own auth journal — taken from evidence, not guessed**, and
both are kept rather than picking one, because excluding the operator is the
single failure that cannot be undone remotely.

**`3f12483` / `e6d9a98` — NetBox bind address.** `NB_BIND` defaulted to
`127.0.0.1` and nothing in the head deploy overrode it. That works on a
single-host sim and breaks the moment the architecture is used as designed.
`gpufab-ops-01` only worked because `NETBOX_BIND` had been set **by hand** at
some point, so the defect stayed invisible until a second sim was built from
scratch: **s3's seed died with `ConnectionError` to `10.10.0.40:8000` while
NetBox sat healthy on `127.0.0.1`.** The follow-up is the instructive half — the
readiness probe was still hardcoded to `127.0.0.1:8000`, so it pointed at a port
nothing listens on and **the deploy stopped at `20-services` on both new sims**.
"Half a fix is its own bug: a health check aimed at the wrong address fails
exactly like a dead service."

## 6. The SoT and seeding

*`seed.py`, `sot_revision.py`, `expected.py`.*

### 6.1 Seeding — an hour to under three minutes, by removing work then overlapping it

**`4472ba1` — pre-fetch and bulk-POST.** A seed was **~10,000 HTTP round trips —
roughly seven per link**. `S1 took over an hour, with the seeder itself at 0% CPU
the whole time. The client was never the bottleneck; the request COUNT was.` Each
collection is now read once into a dict; the REST API accepts a list, so **1466
cables go in ~15 requests**. Threads were explicitly rejected at this step:
NetBox was already at 350% of 4 cores, and parallel writes race the
cable-termination constraints that produced the duplicate-termination crash this
seed already had once. Idempotency is *strengthened* — it now compares against a
full snapshot rather than a per-object GET that could race its own POST.

**`02717a4`** — pynetbox paginates at the server default of 50, so pre-fetching
S1's ~4400 IP addresses was **88 requests**, reintroducing inside the pre-fetch
exactly the cost the pre-fetch exists to remove. 1000 is NetBox's `MAX_PAGE_SIZE`.

**`4f918de` — parallel bulk POSTs.** Cable creation ran at **~3.7/sec**, and the
top two hypotheses were both wrong. Measured on `gpufab-s4-ops` (NetBox 4.3.7, 4
vCPU) during a 100-cable bulk POST: **the netbox container sat at 99% CPU — one
core — postgres at 21%, and three of nginx-unit's four worker processes recorded
0 jiffies.** py-spy on the busy worker, 5647 samples, inside `POST /cables`:

```
enqueue_event -> serialize_for_event   48.8%
save + response serialize              23.2%
validation                              9.0%
changelog (to_objectchange)            10.7%
CablePath                               8.3%
```

An ORM-level A/B on the same box, toggling one layer at a time over 60 cables:

```
full                283.8 ms/cable
events off           95.3            -> events    188.6 ms  66.4%
+changelog off       78.4            -> changelog  16.8 ms   5.9%
+cablepath off       53.6            -> cablepath  24.8 ms   8.7%
```

The cost is `enqueue_event` building a full DRF serializer for every changed
object, and a cable changes five (the Cable, two CableTerminations, and both
Interfaces). **That work cannot be configured away** — `enqueue_event` checks
only whether the *model* supports event rules, never whether one exists: disabling
the gitops rule moved cables from **3.74 to 4.45/sec and no further**.

Spreading the same batches over four connections: **3.74 → 8.31 cables/sec
(2.2x)**, prefixes **30.4 → 61.9/sec**, IP addresses **29.5 → 28.9 (unchanged, so
this stays uniform rather than special-cased)**. With the event rule also
quiesced, **11.55/sec**. For S1's 1466 cables that is **392s → 176s**.

Each thread gets its own pynetbox client because `requests.Session` shares mutable
header and cookie state; endpoints are handed out by static round-robin.

### 6.2 `sot_revision` — the fingerprint

`ca6f8a3`: NetBox 4.x moved the changelog from `/api/extras/object-changes` to
`/api/core/object-changes`, and the old path 404s — **so this had been returning
`changelog_id -1`, its "unavailable" sentinel, on every render since the
upgrade. The sentinel worked exactly as designed and nobody was reading it.**
Also switched to raw HTTP: `pynetbox`'s `.filter(limit=1)` sets the **page size**
to one and paginates the entire changelog, turning a 47ms probe into a 60s hang.

`e689189`: `sot_revision` fingerprinted the SoT with `list(nb.dcim.cables.all())`,
**which made the `gen_topoview` fix pointless — topoview was moved off cables and
its build still took 208s, because the fingerprint computed alongside it walked
straight back into the same query.** `render_fabric_ztp` had it too, and *that
one is on the deploy path*. Both now group cabled interfaces by cable id. The
fingerprint is unchanged in meaning; **its value changes**, because the old string
used termination names in NetBox's arbitrary a/b order — sorting the pair means a
render is no longer spuriously stale because NetBox returned the same cable's ends
the other way round.

`4d4ad0e`: `brief=1` on the fingerprint fetch (see §7 for the measurement).

### 6.3 `expected.py` (new) — one place that says how many of X should exist

**`b2390cf`.** Every check in this project needed an expected number and each
invented its own:

- the health gate asked `gpufab.py` and got **30 switches for a 48-switch
  fabric**;
- the dashboard summed two sims and reported **477 sessions for a 249-session
  fabric**;
- a convergence check compared container count to device count and **called an
  unrouted fabric complete**.

*In each case the OBSERVED side was fine and the EXPECTED side was improvised.*
`expected.py` derives every count from the profile through `fabric_model`, the
same derivation that builds the topology. Cross-checked against values measured
independently on the running fabric: **devices 124, cables 1466, cabled
interfaces 2932, IP addresses 3024, qemu VMs 48, clab nodes 124 — all exact.**

Sessions and peer series are reported **separately** rather than conflated: a
check comparing the wrong one is off by 2x and looks merely "close". `--key`
exits non-zero on failure and writes to stderr, so a caller doing
`n=$(expected.py --key …)` cannot receive an empty string and treat it as zero.

**`ef56238` corrected two expected numbers that were wrong in opposite
directions**, together producing a 1464-vs-1462 "drift" that was neither:

- `bgp_sessions` counted the **OOB fabric**. OOB is a flat L2 management segment:
  `fabric_model` gives its 78 links `p2p=False` and no addresses, NetBox assigns
  none, the renderer emits neither `INTERFACE` nor `BGP_NEIGHBOR`, and the two
  OOB switches ship with an empty `INTERFACE` table. **76 sessions were in the
  denominator that nothing anywhere ever tried to establish. 1462 → 1386.**
- `bgp_peer_series` asserted series == sessions. The exporter emits one
  `gpufab_bgp_peer_up` per (switch, peer), so a switch↔switch session yields
  **two** series while a switch↔host session yields one. Derived now as
  `2*sw_sw + sw_host` = **1464 — exactly what the exporter publishes** — and 1308
  for the host metric, exactly what it publishes there. **The exporter was right
  the whole time; the number it was compared against described a different
  quantity.**

Also adds `max_ports_per_switch`, which is **52 for s1-512 against a 32-port
HWSKU** — the fabric's actual defect, stated as a number the expected side can
hold.

### 7.1 The "477 BGP sessions" incident, and the cross-sim boundary

The landing page reported **"477 BGP sessions up / 477" for a fabric with 249**.
Both its queries are unscoped sums; **this ops host was federating two sims**, so
the page was adding an unrelated simulator's 228 sessions to this one's 249.
Nothing said two systems had been summed, and 477/477 looks healthy. It was
wrong for days while every check said it was fine.

The fix arc is instructive because **three successive "fixes" all failed
silently**:

1. `e45a1bd` scoped every panel to a `$fabric_host` template variable. Still
   showed 477.
2. `6d2cc33`: Grafana's file provisioner **imports into its own database and will
   not re-import unless the dashboard version advances** — the file said one thing
   and the UI showed another. `id:null` forces a fresh insert.
3. `77f84d5`: the template variable **had no datasource**. A Grafana query
   variable without one cannot run `label_values()`, so it never populates and
   `$fabric_host` never interpolates — **and an unresolved variable degrades to
   showing everything rather than to an error.**

`e853db7` then fixed it at the right layer: **scrape only this sim's fabric
hosts (§5.6).** "A dropdown is not a boundary: the other sim's data stays
present, selectable, and summable by any panel added later." Scraping only this
sim makes the wrong answer **unrepresentable** rather than merely un-selected.
`9223d01` removes the variable from both dashboards — with one sim in the data an
unscoped sum is correct by construction — and gives the landing page a real
identity read live from `gpufab_sim_info`, which **turns red and says the stats
below are a SUM** if more than one sim ever appears.

**Sim identity** (`c3be4ba`, `b2d4071`, `e89402b`): `gpufab_sim_info` resolved
`sim_id` by reading files **no stage has ever written**, so it reported
`sim_id="unknown"` on every host — "worse than absent, because it looks like an
answer". Ownership moved to the ops host (§5.6 makes it 1:1 with a sim; §5.4
makes fabric hosts stateless, so an identity living there would change on every
rebuild — precisely when you most need it stable). `sim_id` derives from the GCP
instance id: unique without coordination, durable across reboots, impossible to
duplicate by copying a state file. Two emitters were avoided deliberately — two
`gpufab_sim_info` series is exactly what the landing page reads as "two sims are
being summed here". The label was also renamed `fabric_host` → `fabric`, because
Prometheus resolves the collision with the job's target label by keeping the
target's value and renaming the metric's own to `exported_fabric_host`.

### 7.2 The exporter

`4a87ca5`: the dashboard read **478 up against 477 total — more sessions
established than exist**, which is impossible in a consistent snapshot.
`prometheus_client` keeps a child series for every label combination ever set, so
when a peer's identity changes (IP-keyed → interface-keyed during a mode
migration) the old series survives and keeps reporting its last value alongside
the new one. **It misreported three times (450, 396, 478) before the fabric's
actual state could be stated, and each time it was read as the fabric
degrading** — "the worst failure available to a monitoring system: once one
number lies, every other number becomes unfalsifiable." Prunes only what
*disappeared*, and is **guarded on having observed something**: if every device
was unreachable this round, pruning would delete the whole fabric's history to
report a confident zero.

`776b0dc`: survive starting before the fabric exists (§1.2).

### 7.3 `/fabric` — the topology projection

**Performance, found by measuring rather than guessing.** Four independent
causes, in the order they were peeled:

- `144f1aa` / `6f20636`: **one render issued 311 API requests** for 43 devices
  and 225 cables, because pynetbox dereferences each cable's terminations lazily.
  Cached on NetBox's changelog high-water mark — **deliberately not a TTL**: "a
  TTL serves a payload that may already be wrong and hopes nobody notices."
  **10.5s → 35ms.**
- `3d00581`: that cache is **pathological during a seed**, because the changelog
  mark moves on every object written. Measured over three minutes of the S1 seed,
  NetBox served **24 device fetches, 23 full cable fetches, and 2 actual cable
  POSTs — 47 full re-serializations for 2 cables of progress.** It is quadratic,
  and **the seed decayed from 38 cables/min to under 1 while this service ate the
  CPU it needed. Stopping topoview took the seed to 74/min — a ~100x difference,
  and the writer was never the slow part.** Now: a key change after a quiet period
  rebuilds; a key change while the SoT is still churning serves the last coherent
  payload and marks it `sot_writing`. *Rebuilding through a burst is also wrong on
  its own terms — a topology read mid-write is a partial fabric, and rendering a
  succession of those is not freshness.*
- `45d648c`: `nb.dcim.cables.all()` — a cable's terminations are **generic
  relations**, so NetBox serializes each through `GenericObjectSerializer`, which
  constructs a fresh DRF serializer per object and rebuilds its entire field set,
  every field resolved through `gettext`. py-spy showed NetBox pinned in exactly
  that stack **with Postgres at 20% — pure Python serialization, not queries.**
  At S1's 1466 cables **a single build exceeded 600s and nginx returned 504.**
- `f774a33`: `brief=1`. Measured on this SoT, same table and same serializer:

  ```
  interfaces cabled=true  FULL    19.7 ms/record
  interfaces cabled=true  BRIEF    4.2 ms/record
  interfaces cabled=false FULL     2.2 ms/record   <- no cable, no path to walk
  devices                 FULL     2.6 ms/record
  ```

  **An interface WITH a cable costs 9x one without, through the same code path** —
  NetBox's full interface serializer includes `connected_endpoints`, which *traces
  the cable path per interface*. A page of 1000 interfaces is 1000 graph
  traversals. "'DRF is slow' was the wrong explanation. The uncabled control is
  what identifies it." **~2900 cabled interfaces go from ~58s to ~12s.**

Net result, recorded in `ed0a2aa`: the same 4 vCPU ops host **builds the S1
projection in 15.9s and serves it in 52ms**.

**Concurrency and correctness.** `5b38e16`: `ThreadingHTTPServer` gives every
request its own thread and with no lock every request arriving during a build
started **another** build — a feedback loop, not plain waste, because concurrent
builds compete for the same CPU-bound NetBox. **py-spy caught every stack sample
sitting in the FIRST NetBox call of `build()`, because builds were perpetually
restarting rather than progressing; in the same two minutes NetBox logged 10
device fetches and 16 interface fetches for what should have been one build.**
The landing page polls every 30s and `/fabric` polls too, so **once a build
exceeds the poll interval the loop is guaranteed, not unlucky** — which is why it
only appeared at S1 scale.

`6f5e7ce`: builds run on a background thread and a request is answered
immediately with either the previous projection or an explicit `building:true`.
Before this the page **rendered blank** — nginx gave up at 60s and an empty canvas
looks exactly like a fabric with no devices. *That ambiguity is the actual
defect.*

`65947fd`: the non-blocking branch served whatever payload existed **without
checking which view it was built for**, so a request for the whole fabric was
answered with a payload built for `scope=dc1-pod001` — **43 devices out of a
124-device SoT, indistinguishable from a fabric that had shrunk.** Same view from
an older SoT is fine to serve; a different level/scope "is not stale, it is an
answer to a different question".

**The layered view.** `377eeb9` / `be51ef9` implement `region > dc > pod > tier >
device` with server-side aggregation, because "a single diagram has a ceiling,
which is the one property this architecture is meant not to have — and it breaks
at S1, the NEXT rung: 1,590 elements is already sluggish, S3 is 13,395, S5 is
105,986." Three failures shipped, and they share a shape: **each produced a JSON
payload with the right node count, the right labels and the right totals, and a
picture that was empty or wrong.**

- **no edges** — pods never touch each other; they meet at the DC core, the core
  has no pod, and `_aggregate()` dropped a device with no key at the current
  level. The S3 pod view drew five disconnected boxes and **zero** edges.
- **no positions** — aggregate nodes carried no `layer`, the page places nodes at
  `y = layer * 190`, and `Number(undefined) * 190` is `NaN`. **Nothing drew at
  all**, and `fit()` then framed the one node that still had a position.
- **no icons** — a first version dropped `icon` from the emitted data. "Same
  lesson, one layer up: found by looking at the picture, not at the payload."

The qualification worth keeping: **a level is skipped when the view spans more
than one unit of the level above it.** A tier is a within-pod object, so a
multi-pod tier view draws ~12 units per pod — 420 at S5 — which is strictly worse
than 35 pods.

`44d7cd6`: the auto-aggregation threshold goes **1500 → 6000**. S1 is **1590
elements** (124 devices, 1466 links) so it fell just over the line and
`level=auto` collapsed the entire fabric to 13 tier nodes — the layered view
behaving exactly as specified and still the wrong answer. 6000 keeps S1 (1590)
and S2 (3332) flat and still aggregates S3 (~20k). `5cdb9e3`: an explicit
`?level=device` can still exceed budget — **S4 at device level is a 14.6 MB body
against 0.04 MB for the level auto would have picked** — so the projection now
reports `view.over_budget` and the breadcrumb says so.

**Icons and tracing.** `12112c3` / `ceff876` replace geometric shapes with inline
SVG rack gear where **tier is in the silhouette, not in a detail you must
count**. Three separate causes made every icon fail to load: percent-encoded data
URIs do not survive (**an unencoded `#` truncates the URI at the first colour**,
and a background-image that fails to parse is not an error — it is simply
absent); an SVG carrying only a `viewBox` has no intrinsic size; and square nodes
crushed the aspect, rendering **every switch as a ~10px dash**. Verified by
screenshotting the live page through a browser engine — ImageMagick's SVG
renderer ignores `stop-opacity` and drew every chassis black, which would have
been "a confident, wrong conclusion leading to a fix of a colour scheme that was
already correct."

`4f52125` / `f96783b`: click traces the uplink path to spine rather than one hop,
and **lists the device names it reached** — "'16x leaf → 4x spine' answers how
many, never which, and which is the entire question when a rail is miscabled."

`21ad36e` is a repair of self-inflicted damage worth flagging to reviewers: **a
previous commit's edit inserted its comment mid-line and swallowed the `fetch`
call with it**, so `load()` referenced an undefined variable and threw. "That
commit claimed the change was applied because the script printed unconditionally
rather than checking; a grep for the new branch afterwards returned 0."

### 8.1 The harness itself

`tests/lib.sh` exists because "ad-hoc verification kept reporting results it had
not measured". Today it was found to contain the same defect:

**`a0a6eed` — `t_zero` must not pass on a measurement that never ran.** Three
`t08` assertions printed PASS while their python heredocs died with
`ModuleNotFoundError` — the traceback went to stderr, stdout was empty, `$got`
defaulted to 0, and **"devices reusing a port: none" was reported by a check that
had not looked at a single link.** `t_zero` now requires a *number*; empty or

### 8.2 The new tests, and what each is for

**`t11-config-applied.sh` (`2032d9e`) — the handover nobody was checking.**
Every stage verified its own step and none verified the join. All of them passed
on `gpufab-s3-fabric` while every switch ran an empty routing config:

```
rendered artifact   34 KB, BGP_NEIGHBOR present, INTERFACE present
the switch          BGP_NEIGHBOR {}, INTERFACE {}, 'BGP instance not found'
```

The fabric reported **159/258 sessions up, of which 153 were HOST sessions** —
configured by a different path. **Switch-to-switch BGP was dead across three
independently built fabrics.** t11 *compares* rather than inspects: what is on
the box must equal what was rendered **for that box** — a switch holding another
switch's config would pass a "does it look configured" check and is equally
broken.

t11 was then fixed four times, each fix a defect of the kind it exists to catch:
`0ff5609` (it printed PASS having compared **zero** switches — "the
measured-nothing pass, reproduced inside the test written to eliminate it"; and
`sw_run` discarded stderr, reporting "port closed", "auth failed" and "command
returned nothing" all as *unreachable*); `05aef39` (`got=$(sw_run …)` runs in a
subshell, so `SW_RC` never reached the caller and `set -u` aborted the test after
two assertions had passed); `7b9d2bd` (`StrictHostKeyChecking=no` **does not
cover a CHANGED host key** — containerlab hands every switch VM a fresh host key
on redeploy, so after any rebuild this test **reported 48 healthy switches as
"unreachable"**, observed on s4 as 2 passed / 8 failed while ssh with
`UserKnownHostsFile=/dev/null` answered on the first attempt; verified by the
failure *moving* from rc=255 to rc=5 "Permission denied", a real and different
condition); `eac30b3` (`n_art=$(ls … | grep -c . || echo 0)` yields `"0\n0"` on an
empty directory, so **on an empty ZTP_DIR this test claimed rendered artifacts
were present**; plus a new assertion that the automation key is usable).

**`t13-bgp-peer-truth.sh` (`69973c5`) — adjudicate each session against the
device that owns it.** `t03` compares the exporter's *total* against the
switches' total, which catches an exporter that is broadly wrong and nothing
else. On `gpufab-s3-fabric` the totals agreed at **1286/1464** and the only
honest description available was **"178 down, unknown which, unknown whether
real"** — not actionable, because "the exporter is wrong" and "the fabric is
broken" demand opposite responses. t13 joins the two views per session:

```
exporter down + device down          -> genuinely down
exporter down + device Established   -> a measurement artifact
exporter up   + device down          -> the worse artifact, silent
peer in exporter, absent on device   -> a stale label set
peer on device, absent in exporter   -> an unmonitored session
```

It **always contacts real devices** — adjudicating only the exporter's down list
"asks the exporter to nominate its own auditor: on a fabric it reports as
converged that list is empty, no device is contacted, and the test would pass
having taken the exporter entirely at its word." Two bugs found by running it:
the `grep -c` / `"0\n0"` defect, and **ssh without `-n` ate the loop's stdin, so
6 selected devices became 1 adjudicated with no error raised** — which passed,
because the assertion under it only demanded "at least 1".

**`t14-port-table.sh` (`16e4e0d`) — the PORT table against the SoT, without a
live NetBox.** "The 178-session defect survived three fabric builds because the
render path could only be exercised on a deployed host against a live SoT — the
only place it was observable was the place where observing it costs a rebuild."
Drives the real `device_config()` against a SoT derived from a profile, on the
workstation. It runs against `s1-512-small`, **whose busiest switch uses 64
ports**, and that choice is the point: **s0-64's busiest uses 13, so every
assertion here would have PASSED on s0-64 for the entire time the bug was live.**
**55 of 59 switches in s1-512-small address more than 32 ports**, and the file
asserts that population is non-empty.

Mutation-tested, **and the first version FAILED it**: reintroducing the
truncation still raised on the count cross-check, "so the suite passed while the
code silently dropped 32 ports". Three mutations are now caught.

**`t15-port-inventory.sh` (`5eabdb6`, `ab689c7`) — the artifacts actually being
SERVED.** Two reasons this file exists. The urgent one: `verify.sh` on main
referenced it and it did not exist in a clean checkout, so nobody could run the
suite. The instructive one is **how its original assertion died — it did not
fail, it PASSED**, reporting "surplus 12", because it read
`len(vs_port_sets[hwsku])` and that file had become a table of per-port
*attributes*. "An assertion that keeps passing after the thing it measures has
changed meaning is worse than one that fails, because nothing draws your eye to
it."

What survives is the one thing `t14` cannot see: `t14` asserts the render
**function**, offline; this asserts the **artifacts on disk**, which are rendered
once and then served indefinitely. **`gpufab-s3-fabric` is serving artifacts
rendered before today's render change right now.** Measured on s3: **48 served
files checked, 0 with an INTERFACE on a port their own PORT table lacks, 0 whose
PORT count disagrees with the catalog, 0 unresolvable against the SoT.**
`ab689c7` adds the render-code assertion, motivated by: **s3 and s4 both stamp
SoT fingerprint `5c0d184d7ee65c49` with 124 devices and 1466 cables while s3
serves 64-row PORT tables and s4 serves 32-row on all 48 switches.**

**`t12-recovery-units.sh` (`c7662f0`) — recovery points at THIS sim's SoT, in
systemd's environment.** "The cross-sim rebuild was invisible to every check that
existed, because they all ran in a login shell where `NETBOX_URL` is set. The
value that was wrong only appears under systemd." It measures what `systemctl
show` has loaded, what the script's own `SOT=` line resolves to under `env -i`
(**extracted from the script rather than restated, so the test cannot drift away
from the code it checks**), and that no NetBox address other than this sim's
appears in the script at all. **Reachability alone would have passed against the
wrong NetBox, and a device count would have too — both sims hold 124. Only
identity separates them.**

**`t16-convergence-phases.sh` (`04a1f51`) — convergence is measured, and no phase
burned its timeout.** Convergence time was an estimate ("30–60 min"). **Measured
it is 22m27s, 14m00s of which was one phase.** The load-bearing assertion is (3):

## 10. Design documentation

*12 commits, all in `design/scale-out-architecture.md` except two new files.*

Each records something that was **learned rather than designed**. In rough
dependency order:

- **§8.0 — S5 does not currently wire** (`80e4f18`, and profile fix `2199853`).
  "Validation that never allocates a physical resource cannot detect a physical
  impossibility." The backend core fans out to every spine, so core port demand
  grows with spine count: **S3 declared 15 cores and needs 16; S4 declared 33 and
  needs 39; S5 needs 248, and then the core mgmt pool is exhausted.** S3/S4 are
  arithmetic and fixed. **S5 should not be fixed by raising the number** — 248
  core switches of 64 ports each is not a core tier, it is an admission that the
  topology is wrong. The honest options are a denser core platform, a 3-tier
  core, or accepting that a single DC tops out below 33K GPUs, which §8.1's
  add-sites growth already makes defensible. **The static suite fails on S5 by
  design, because a skipped check restores exactly the silence that hid this.**
- **§8.0a — host sizing must count nodes** (`dc8c237`). The per-VM figure was
  nearly right (**4.12 GB actual vs 4.00 assumed**); what was wrong is what it was
  applied to. Also records the consequence that matters more than the number:
  **S2 is the first rung that fits no single machine, and `fabric_host_count=2`
  does not yet produce a fabric — it produces two disconnected half-fabrics.**
  (`86c8f44` later built the VXLAN sharding that closes this.)
- **§2.5.3 and §4.2 — the fabric view must be layered / as built** (`27cfded`,
  `381227a`, `a9e3f41`). Records the level hierarchy, the selection rule and its
  one qualification, and the three failures that shipped. Plus the verification
  note that generalises: **verify with the engine that will run the thing, not
  the one that is convenient.**
- **§5.6 — one ops host per sim: isolation, not filtering** (`dc48e89`). "A
  fabric_host dropdown does not provide a tenancy boundary: every user sees every
  sim in the list, any user can switch, and one Prometheus holds all of their
  data." Records the costs honestly — **cross-sim comparison is lost
  deliberately**, VM count grows with sims, and "exactly 1 head per DC" becomes "1
  per sim per DC" — and what it does not solve: two sims still share a project, a
  VPC and the substrate.
- **§5.6.1 — making `ops.tf` countable is a state migration, not an edit**
  (`5ccaa86`). Adding `count` renames the resource to `.ops[0]`, which terraform
  reads as destroy-and-create — and the ops host holds NetBox and Prometheus.
  **Timing sharpens it: had `ops.tf` been made countable first, the §8.0a
  machine-type apply would have silently included destroying the SoT, and a plan
  reading "1 to add, 1 to destroy" looks unremarkable.** General rule: **check a
  plan for what it DESTROYS, not for whether it resembles the change you
  intended.**
- **§5.6.2 — the isolation boundary was breached by a shell default**
  (`34f2bf6`). The stage 98 quoted-heredoc defect (§5.1), recorded **because of
  why it was invisible**: every sim is seeded from the same profile, so both
  NetBoxes answer 200 with 124 devices and the rebuild's own guard passes against
  the wrong sim exactly as convincingly. **The rule: a value that must differ per
  sim must never have a cross-sim default. A wrong default that names a real,
  reachable, plausible peer is worse than no value.**
- **§9 — static analysis before anything boots** (`2dcf26e`). The argument that
  makes Batfish necessary: **every check this system trusts requires a running
  fabric, and §8.0a shows the ladder runs out of hosts long before 200–500K.**
  Documents the trap that makes a naive integration *actively dangerous*:
  **Batfish's SONiC backend parses 17 config_db tables and `BGP_NEIGHBOR` is not
  one of them. It drops the table with a warning, builds a model with ZERO BGP
  sessions, and still reports the snapshot as parsed successfully** — so "are any
  sessions failing?" answers no. **A green run against config_db alone would be
  the most dangerous artifact in the system.** Also lists what it would *not*
  have caught.
- **§4.1.1 — hardware tables come from the SoT, never a snapshot** (`f5341ad`).
  The general rule the PORT defect instantiates, plus two corollaries learned
  rather than designed: **one origin beats two agreeing origins**, and **a
  SoT/catalog disagreement is fatal rather than a warning.** Records the rest of
  the `vs_base_config_db.json` audit — `FEATURE/LOGGER/VERSIONS/
  FLEX_COUNTER_TABLE` describe the image it was captured from and carry the same
  staleness risk one level down.
- **§4.1.2 — provenance must cover the transform** (`b2be72a`, `31840b0`). The
  two-host measurement, and the two things learned from first real use: the
  content hash **caught another agent's uncommitted edit by content** (no commit
  id could have), and the host sync was cut from `git archive HEAD` minutes
  before that edit appeared — **a working tree has no atomicity, and syncing from
  one ships whatever someone is midway through.**
- **`HANDOFF-2026-07-26.md`** (`ae2e0c1`, new). Fleet table, per-sim dashboard
  tunnels, in-flight agents. Leads with the thing that will mislead a reader:
  **no host can `git pull`, so host-side `git status` is not a drift signal** —
  every checkout has only been updated by tar+scp and shows correct `main`
  content as "modified". Only a workstation-side checksum comparison is
  trustworthy.
- **`runbooks/start-stop.md`** (`2e4db2f`, new). One real preemption drill, every
  number from that run, **including what did not finish** (§1.5).

7. **`t16-convergence-phases.sh` is not in `verify.sh`.** It was committed

## 14. The pattern behind almost all of it

Worth stating once, because it is the reason this many commits landed in one day
and the best predictor of where the next bug will be:

> **A check that reported success having measured nothing.**

The same shape, in every subsystem today: `|| true` on the apply step; `grep -c`
returning `"0\n0"` so a comparison errors and the assertion prints PASS; a
readiness loop that falls out and continues; `wait_healthy` using string equality;
`t_zero` passing on empty input; a recovery path that ran zero stages and printed
"complete"; a zero-byte credential file; a 403 read as unreachable; an unresolved
Grafana variable degrading to "show everything"; an assertion that kept passing
after the thing it measured changed meaning.

The countermeasures now in place, and what to prefer over improvised checks:

- **`tests/lib.sh`** — assertions take an observed count; zero observations is a
  failure, and a non-numeric observation is a failure.
- **`tools/expected.py`** — one derivation of what should exist, never a literal.
- **`t11` / `t13` / `test_config_landed.py`** — compare against the device, not
  against a metric; and where possible make the comparison a pure function that
  runs before anything is deployed.
- **`render_revision.py`** — provenance over the transform, not only the input.
- **`verify.sh` phase ordering** — the thing that detects staleness must not be
  shipped by the mechanism that goes stale.
