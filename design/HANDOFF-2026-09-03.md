**Read this header first.** This document is append-only. Where it disagrees with

else in `HANDOFF-2026-09-02.md` still stands.

## 1. What the ownership engine is, and why it exists

`deploy/checks/c11-unit-labs-one-host.sh` is FROZEN and superseded. It grew to
about 300 lines of shell, and the same ownership defect was found in it three
separate times — once per resource kind. Cleanup deleted bridges it had refused
to adopt, then destroyed labs it had not deployed, then removed docker networks
it had not created. Each fix was correct and local, and the next review found the
same class one resource over.

The strategy changed in response: state the rule ONCE, make every resource an
instance of it, and build the adversarial harness before the executor.

    tools/ownership.py     the policy engine — no host contact at all
    tools/host_drivers.py  the adapter — the only file that issues real commands
    tools/unit_executor.py the plan and the transaction driver
    deploy/checks/c12-unit-labs.sh  a thin launcher, no ownership logic

The invariant, frozen and quoted verbatim in the code:

> A resource may be mutated only after its state was successfully measured,
> ownership was recorded before mutation, cleanup touches only recorded
> ownership, and success requires every owned resource measured at its final
> state. Unknown always refuses.

Two tables encode it. `TABLE` has 24 cells keyed `(op, State, owned)`;
`ACQUIRE_TABLE` has 18 keyed `(created_ok, State, Ready)` of which **exactly one**
returns OK. Both are asserted in `t81` against expectations WRITTEN OUT BY HAND
from the invariant, with a length assertion so a new cell in the module cannot
appear untested. This matters specifically because `ACQUIRE_TABLE` is built by a
comprehension: a test that looped over it and re-applied the rule would agree
with itself and prove nothing.

## 2. The traps a fresh reader will hit

**Ownership is the LEDGER, not the resource.** `PRESENT_FOREIGN` is derived
(`PRESENT ∧ ¬ledgered`), never stored. Do not add a state for it.

**Three-valued observation.** ABSENT / PRESENT / UNKNOWN. A command that failed
yields UNKNOWN, never ABSENT. Every observation LISTS the whole namespace once
and tests membership, because `ip link show br0` and `docker network inspect X`
both exit non-zero for "absent" AND for "the tool could not run", and treating
those alike is how a failed measurement becomes "safe to proceed".

**Readiness is a SEPARATE axis from existence.** A bridge that exists but is DOWN
carries nothing; a network with the wrong subnet is not the network R asked for;
a lab with a subset of its containers is a partial deploy, not a lab.

**Lab membership comes from docker's `containerlab=<lab>` label, never the
container name.** `clab-<lab>-<node>` is ambiguous under concatenation: lab `c12`
with a node named `core-n1` produces exactly what lab `c12-core` with node `n1`
produces. Measured on the live host, the old name-prefix rule claimed labs
`gpufab-dc1` and `gpufab-dc1-pod001` existed; neither ever has.

**The network is created by US, not by clab.** Letting clab create it leaves a
resource we did not record and cannot certify, and clab picks the subnet — which
is precisely how three unit labs came to share one network name.

**An empty live-fabric snapshot is not automatically a safe one.** `[]` compares
equal to `[]` and the guard goes green having observed nothing. `[]` is the
correct answer on a host carrying no fabric and is ALSO what a guard looking
under the wrong name returns; the two are indistinguishable from inside
`execute()`, so the operator declares which with `--allow-no-live-fabric`. On
`gpufab-fabric-01` that flag must NOT be passed.

**The live-fabric guard has three parts and two container name shapes.**
`clab-gpufab*` is the lab; `gpufab-*` catches `gpufab-ztp-oob` and
`gpufab-tacacs`, which carry no containerlab label at all yet are the containers
without which the fabric cannot boot. Monitoring containers are deliberately
excluded — they restart on their own schedule and nothing the executor does can
reach them. Beyond containers the snapshot carries **production docker networks by
name AND Id** and **every host bridge**, because a containers-only snapshot could
not see either resource kind this executor actually creates and deletes: removing
a bridge or a network left `before == after` byte-for-byte.

**Ownership is proven, not claimed.** `record()` runs BEFORE the mutation, so it
is a claim on a NAME and not evidence that we made the object. Confirmation is
written only when `create` returned True and the object is PRESENT, and it carries
the object's identity. Cleanup deletes only what it can prove this run made;
anything else is reported and left in place. **Authorship is not acquisition** — a
bridge we created but could not bring UP is still ours to remove, so confirmation
precedes the readiness verdict rather than following it.

**Existence asks `docker ps -a`; readiness must not.** A stopped container still
exists and still has to be cleaned, but a node that is not running carries nothing.
Reading readiness from `-a` made a lab of dead containers READY.

**c12 relocates management addressing.** The micro fixture's pod-001 management
subnet is `172.20.0.0/24`, which IS the live `gpufab-oob` network, so
`docker network create` refuses with a pool overlap. The launcher derives a
relocated profile at `172.28.0.0/22` rather than editing the fixture, whose map
is frozen by `t77`.

Each suite now declares an **assertion floor**. Every one of them used to exit 0

## 4. Two rounds of review, and what they cost

**Round 1 (self-review)** found six defects — lab existence by name prefix, a
driver exception escaping as a traceback, an empty live-fabric snapshot passing
while measuring nothing, a guard blind to `gpufab-ztp-oob`/`gpufab-tacacs`, a test
hole found only by mutation, and 18 untested `ACQUIRE_TABLE` cells. Ladder went to
149 assertions, 12 mutations killed.

**Round 2** ran three INDEPENDENT adversarial passes over `935a110`, each with a
different lens, each required to produce an executed reproduction rather than an
argument. They found **19 more defects that the 149-assertion ladder could not
see**, including 17 surviving mutations. Every one has been fixed; the ladder is
now 207 and 31 mutations are killed.

The shape of that result is the lesson:

> The ownership POLICY engine was genuinely well verified — every table cell
> hand-authored, ordering and record-before-mutate proven, controls all killed.
> **Verification stopped at the policy boundary.** Everything the policy delegates
> to — the commands actually issued to the host, the readiness judgements fed back
> into the acquisition table, the top-level rc the caller reads, and the guard
> protecting 126 live containers — is where all 17 surviving mutations lived. The
> suite proved the engine DECIDES correctly and never proved it DOES anything
> correctly.

The four worst, each demonstrated with a running reproduction:

1. **The ledger recorded intent, not authorship.** `record()` must run before the
   mutation, so when `create` failed because the resource ALREADY EXISTED — a
   foreign actor creating it between preflight and create — the name sat in our
   ledger while the object was someone else's, and cleanup deleted it. Reproduced
   with two real processes: B's create failed EEXIST and B then deleted A's live
   bridge, while A returned 0 and logged "live fabric identical after the run".
   Cleanup now deletes only what it can prove this run made, and confirmation
   carries the object's IDENTITY (bridge ifindex+MAC, docker network Id, container
   Ids) so a resource replaced during a long deploy is refused rather than removed.
   **Authorship is not acquisition** — a bridge we created but could not bring UP
   is still ours to remove, so confirmation precedes the readiness verdict.
2. **`c12 --recover` could never do anything.** The ledger defaulted into
   `$SCRATCH`, a fresh `mktemp -d` per invocation, so the documented recovery
   command always read a ledger created empty microseconds earlier: it adopted 0
   entries, released nothing, and printed `c12 VERDICT: OK` with the crashed run's
   wreckage still on the host. The engine's recovery path was sound — the
   disposable-host fault injection passed `--ledger` explicitly — and only the
   launcher's default made it unreachable. The lock was already stable; the ledger
   now is too.
3. **A lab of dead containers was certified READY.** Readiness read `docker ps -a`,
   which lists exited containers exactly like running ones, so readiness measured
   nothing existence had not, and `containerlab deploy` returning rc=0 was the only
   thing the acquire path actually trusted.
4. **The guard could not see either resource kind this executor manipulates.** It
   snapshotted containers only, so deleting a host bridge or a docker network left
   `before == after` byte-for-byte. Every foreign-mutation reproduction in the
   review ended with the line "live fabric identical after the run".

Also fixed: cleanup could suppress the guard entirely (a raise in the `finally`
escaped with no verdict and skipped the after-snapshot); a failed cleanup could not
raise a VOID to FAIL because `rc = rc or 1` leaves 2 intact; c12 forwarded every
argument AFTER its own so `--lock` silently replaced the host lock; the lab was
measured by label but mutated by name; `prefix` and `mgmt.bridge` were unvalidated;
`delete()` was called by no test at all, so `docker network rm` could become
`docker network prune -f` — which removes every unused network on the host —
unnoticed.

Three findings were about the tests themselves: a literal `check(True, True)`
tautology, a mutation-count assertion that laundered "not measured" into a count
three ways in one expression, and the missing assertion floors.

## 5. What the reviewers could NOT settle

Named here because an unexamined path is worth more written down than assumed
safe. All three were offline by construction (no host contact), so anything
resting on real containerlab or docker behaviour is unverified:

- **The real blast radius of `containerlab destroy -t <topo> --cleanup` on clab
  0.77** — whether it selects containers by the `containerlab=` label or by
  derived names, whether it removes the mgmt docker network and its `DOCKER-USER`
  iptables rules, whether it touches `kind: bridge` nodes, and exactly what
  `--cleanup` removes. This is the multiplier on the measure/mutate split.
- **clab 0.77's `prefix` and `mgmt.bridge` semantics.** Both are now refused
  outright rather than reasoned about.
- **Whether `docker network rm` on a network with foreign endpoints is refused by
  the daemon** in this docker version.
- **Whether c12's content-hash bridge names can collide with the live fabric's.**
  The names are un-namespaced hashes of the link. A collision fails closed at
  preflight, but it is the enabling condition for the recover path above.
- **Behaviour under real root/`sudo`, `/var/lock` permissions, and real `flock`
  semantics** on the host filesystem.

## 7. If you change this code

The rule that produced the current state, and the reason it is worth the
friction: **express the invariant once, and make every new resource an instance
of it.** The predecessor's three identical defects were not three mistakes; they
were one mistake made three times because the rule lived in three places.

Concretely: do not add ownership logic to `c12-unit-labs.sh` or to any future
launcher. A launcher generates artifacts and calls the executor. If a new rule
seems to belong in the launcher, it belongs in `ownership.py`, and it needs a
hand-authored cell in `t81` before it needs an implementation.
