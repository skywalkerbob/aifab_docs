## 1. What the ownership engine is, and why it exists

`deploy/checks/c11-unit-labs-one-host.sh` is FROZEN and superseded. It grew to
about 300 lines of shell, and the same ownership defect was found in it three
separate times — once per resource kind. Cleanup deleted bridges it had refused
to adopt, then destroyed labs it had not deployed, then removed docker networks
it had not created. Each fix was correct and local, and the next review found the
same class one resource over.

The strategy changed in response: state the rule ONCE, make every resource an
instance of it, and build the adversarial harness before the executor.

    tools/ownership.py     the policy engine — no host contact at all
    tools/host_drivers.py  the adapter — the only file that issues real commands
    tools/unit_executor.py the plan and the transaction driver
    deploy/checks/c12-unit-labs.sh  a thin launcher, no ownership logic

The invariant, frozen and quoted verbatim in the code:

> A resource may be mutated only after its state was successfully measured,
> ownership was recorded before mutation, cleanup touches only recorded
> ownership, and success requires every owned resource measured at its final
> state. Unknown always refuses.

Two tables encode it. `TABLE` has 24 cells keyed `(op, State, owned)`;
`ACQUIRE_TABLE` has 18 keyed `(created_ok, State, Ready)` of which **exactly one**
returns OK. Both are asserted in `t81` against expectations WRITTEN OUT BY HAND
from the invariant, with a length assertion so a new cell in the module cannot
appear untested. This matters specifically because `ACQUIRE_TABLE` is built by a
comprehension: a test that looped over it and re-applied the rule would agree
with itself and prove nothing.

## 2. The traps a fresh reader will hit

**Ownership is the LEDGER, not the resource.** `PRESENT_FOREIGN` is derived
(`PRESENT ∧ ¬ledgered`), never stored. Do not add a state for it.

**Three-valued observation.** ABSENT / PRESENT / UNKNOWN. A command that failed
yields UNKNOWN, never ABSENT. Every observation LISTS the whole namespace once
and tests membership, because `ip link show br0` and `docker network inspect X`
both exit non-zero for "absent" AND for "the tool could not run", and treating
those alike is how a failed measurement becomes "safe to proceed".

**Readiness is a SEPARATE axis from existence.** A bridge that exists but is DOWN
carries nothing; a network with the wrong subnet is not the network R asked for;
a lab with a subset of its containers is a partial deploy, not a lab.

**Lab membership comes from docker's `containerlab=<lab>` label, never the
container name.** `clab-<lab>-<node>` is ambiguous under concatenation: lab `c12`
with a node named `core-n1` produces exactly what lab `c12-core` with node `n1`
produces. Measured on the live host, the old name-prefix rule claimed labs
`gpufab-dc1` and `gpufab-dc1-pod001` existed; neither ever has.

**The network is created by US, not by clab.** Letting clab create it leaves a
resource we did not record and cannot certify, and clab picks the subnet — which
is precisely how three unit labs came to share one network name.

**An empty live-fabric snapshot is not automatically a safe one.** `[]` compares
equal to `[]` and the guard goes green having observed nothing. `[]` is the
correct answer on a host carrying no fabric and is ALSO what a guard looking
under the wrong name returns; the two are indistinguishable from inside
`execute()`, so the operator declares which with `--allow-no-live-fabric`. On
`gpufab-fabric-01` that flag must NOT be passed.

**The live-fabric guard covers two name shapes.** `clab-gpufab*` is the lab;
`gpufab-*` catches `gpufab-ztp-oob` and `gpufab-tacacs`, which carry no
containerlab label at all yet are the containers without which the fabric cannot
boot. Monitoring containers are deliberately excluded — they restart on their own
schedule and nothing the executor does can reach them, so including them would
manufacture failures rather than catch them.

**c12 relocates management addressing.** The micro fixture's pod-001 management
subnet is `172.20.0.0/24`, which IS the live `gpufab-oob` network, so
`docker network create` refuses with a pool overlap. The launcher derives a
relocated profile at `172.28.0.0/22` rather than editing the fixture, whose map
is frozen by `t77`.

and was scored as a survival. The harness now fails loudly when a mutation does
not apply. **A mutation that did not apply measured nothing.**

## 7. If you change this code

The rule that produced the current state, and the reason it is worth the
friction: **express the invariant once, and make every new resource an instance
of it.** The predecessor's three identical defects were not three mistakes; they
were one mistake made three times because the rule lived in three places.

Concretely: do not add ownership logic to `c12-unit-labs.sh` or to any future
launcher. A launcher generates artifacts and calls the executor. If a new rule
seems to belong in the launcher, it belongs in `ownership.py`, and it needs a
hand-authored cell in `t81` before it needs an implementation.
