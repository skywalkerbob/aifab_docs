**Read this header first.** This document is append-only. Where it disagrees with
an older handoff, this one wins for the ownership engine and c12 only; everything
else in `HANDOFF-2026-09-02.md` still stands.

State at the time of writing: `gpufab-platform` HEAD is `6b7866f`, identical to
`origin/main`, working tree clean. Two rounds of review are COMPLETE and every
finding is fixed and pushed (see §4). Nothing is uncommitted and nothing is

## 1. What the ownership engine is, and why it exists

`deploy/checks/c11-unit-labs-one-host.sh` is FROZEN and superseded. It grew to
about 300 lines of shell, and the same ownership defect was found in it three
separate times — once per resource kind. Cleanup deleted bridges it had refused
to adopt, then destroyed labs it had not deployed, then removed docker networks
it had not created. Each fix was correct and local, and the next review found the
same class one resource over.

The strategy changed in response: state the rule ONCE, make every resource an
instance of it, and build the adversarial harness before the executor.

    tools/ownership.py     the policy engine — no host contact at all
    tools/host_drivers.py  the adapter — the only file that issues real commands
    tools/unit_executor.py the plan and the transaction driver
    deploy/checks/c12-unit-labs.sh  a thin launcher, no ownership logic

The invariant, frozen and quoted verbatim in the code:

> A resource may be mutated only after its state was successfully measured,
> ownership was recorded before mutation, cleanup touches only recorded
> ownership, and success requires every owned resource measured at its final
> state. Unknown always refuses.

Two tables encode it. `TABLE` has 24 cells keyed `(op, State, owned)`;
`ACQUIRE_TABLE` has 18 keyed `(created_ok, State, Ready)` of which **exactly one**
returns OK. Both are asserted in `t81` against expectations WRITTEN OUT BY HAND
from the invariant, with a length assertion so a new cell in the module cannot
appear untested. This matters specifically because `ACQUIRE_TABLE` is built by a
comprehension: a test that looped over it and re-applied the rule would agree
with itself and prove nothing.

## 2. The traps a fresh reader will hit

**Ownership is the LEDGER, not the resource.** `PRESENT_FOREIGN` is derived
(`PRESENT ∧ ¬ledgered`), never stored. Do not add a state for it.

**Three-valued observation.** ABSENT / PRESENT / UNKNOWN. A command that failed
yields UNKNOWN, never ABSENT. Every observation LISTS the whole namespace once
and tests membership, because `ip link show br0` and `docker network inspect X`
both exit non-zero for "absent" AND for "the tool could not run", and treating
those alike is how a failed measurement becomes "safe to proceed".

**Readiness is a SEPARATE axis from existence.** A bridge that exists but is DOWN
carries nothing; a network with the wrong subnet is not the network R asked for;
a lab with a subset of its containers is a partial deploy, not a lab.

**Lab membership comes from docker's `containerlab=<lab>` label, never the
container name.** `clab-<lab>-<node>` is ambiguous under concatenation: lab `c12`
with a node named `core-n1` produces exactly what lab `c12-core` with node `n1`
produces. Measured on the live host, the old name-prefix rule claimed labs
`gpufab-dc1` and `gpufab-dc1-pod001` existed; neither ever has.

**The network is created by US, not by clab.** Letting clab create it leaves a
resource we did not record and cannot certify, and clab picks the subnet — which
is precisely how three unit labs came to share one network name.

**An empty live-fabric snapshot is not automatically a safe one.** `[]` compares
equal to `[]` and the guard goes green having observed nothing. `[]` is the
correct answer on a host carrying no fabric and is ALSO what a guard looking
under the wrong name returns; the two are indistinguishable from inside
`execute()`, so the operator declares which with `--allow-no-live-fabric`. On
`gpufab-fabric-01` that flag must NOT be passed.

**The live-fabric guard has three parts and two container name shapes.**
`clab-gpufab*` is the lab; `gpufab-*` catches `gpufab-ztp-oob` and
`gpufab-tacacs`, which carry no containerlab label at all yet are the containers
without which the fabric cannot boot. Monitoring containers are deliberately
excluded — they restart on their own schedule and nothing the executor does can
reach them. Beyond containers the snapshot carries **production docker networks by
name AND Id** and **every host bridge**, because a containers-only snapshot could
not see either resource kind this executor actually creates and deletes: removing
a bridge or a network left `before == after` byte-for-byte.

**Ownership is proven, not claimed.** `record()` runs BEFORE the mutation, so it
is a claim on a NAME and not evidence that we made the object. Confirmation is
written only when `create` returned True and the object is PRESENT, and it carries
the object's identity. Cleanup deletes only what it can prove this run made;
anything else is reported and left in place. **Authorship is not acquisition** — a
bridge we created but could not bring UP is still ours to remove, so confirmation
precedes the readiness verdict rather than following it.

**Existence asks `docker ps -a`; readiness must not.** A stopped container still
exists and still has to be cleaned, but a node that is not running carries nothing.
Reading readiness from `-a` made a lab of dead containers READY.

**c12 relocates management addressing.** The micro fixture's pod-001 management
subnet is `172.20.0.0/24`, which IS the live `gpufab-oob` network, so
`docker network create` refuses with a pool overlap. The launcher derives a
relocated profile at `172.28.0.0/22` rather than editing the fixture, whose map
is frozen by `t77`.

## 4. Two rounds of review, and what they cost

**Round 1 (self-review)** found six defects — lab existence by name prefix, a
driver exception escaping as a traceback, an empty live-fabric snapshot passing
while measuring nothing, a guard blind to `gpufab-ztp-oob`/`gpufab-tacacs`, a test
hole found only by mutation, and 18 untested `ACQUIRE_TABLE` cells. Ladder went to
149 assertions, 12 mutations killed.

**Round 2** ran three INDEPENDENT adversarial passes over `935a110`, each with a
different lens, each required to produce an executed reproduction rather than an
argument. They found **19 more defects that the 149-assertion ladder could not
see**, including 17 surviving mutations. Every one has been fixed; the ladder is
now 207 and 31 mutations are killed.

The shape of that result is the lesson:

> The ownership POLICY engine was genuinely well verified — every table cell
> hand-authored, ordering and record-before-mutate proven, controls all killed.
> **Verification stopped at the policy boundary.** Everything the policy delegates
> to — the commands actually issued to the host, the readiness judgements fed back
> into the acquisition table, the top-level rc the caller reads, and the guard
> protecting 126 live containers — is where all 17 surviving mutations lived. The
> suite proved the engine DECIDES correctly and never proved it DOES anything
> correctly.

The four worst, each demonstrated with a running reproduction:

1. **The ledger recorded intent, not authorship.** `record()` must run before the
   mutation, so when `create` failed because the resource ALREADY EXISTED — a
   foreign actor creating it between preflight and create — the name sat in our
   ledger while the object was someone else's, and cleanup deleted it. Reproduced
   with two real processes: B's create failed EEXIST and B then deleted A's live
   bridge, while A returned 0 and logged "live fabric identical after the run".
   Cleanup now deletes only what it can prove this run made, and confirmation
   carries the object's IDENTITY (bridge ifindex+MAC, docker network Id, container
   Ids) so a resource replaced during a long deploy is refused rather than removed.
   **Authorship is not acquisition** — a bridge we created but could not bring UP
   is still ours to remove, so confirmation precedes the readiness verdict.
2. **`c12 --recover` could never do anything.** The ledger defaulted into
   `$SCRATCH`, a fresh `mktemp -d` per invocation, so the documented recovery
   command always read a ledger created empty microseconds earlier: it adopted 0
   entries, released nothing, and printed `c12 VERDICT: OK` with the crashed run's
   wreckage still on the host. The engine's recovery path was sound — the
   disposable-host fault injection passed `--ledger` explicitly — and only the
   launcher's default made it unreachable. The lock was already stable; the ledger
   now is too.
3. **A lab of dead containers was certified READY.** Readiness read `docker ps -a`,
   which lists exited containers exactly like running ones, so readiness measured
   nothing existence had not, and `containerlab deploy` returning rc=0 was the only
   thing the acquire path actually trusted.
4. **The guard could not see either resource kind this executor manipulates.** It
   snapshotted containers only, so deleting a host bridge or a docker network left
   `before == after` byte-for-byte. Every foreign-mutation reproduction in the
   review ended with the line "live fabric identical after the run".

Also fixed: cleanup could suppress the guard entirely (a raise in the `finally`
escaped with no verdict and skipped the after-snapshot); a failed cleanup could not
raise a VOID to FAIL because `rc = rc or 1` leaves 2 intact; c12 forwarded every
argument AFTER its own so `--lock` silently replaced the host lock; the lab was
measured by label but mutated by name; `prefix` and `mgmt.bridge` were unvalidated;
`delete()` was called by no test at all, so `docker network rm` could become
`docker network prune -f` — which removes every unused network on the host —
unnoticed.

Three findings were about the tests themselves: a literal `check(True, True)`
tautology, a mutation-count assertion that laundered "not measured" into a count
three ways in one expression, and the missing assertion floors.

## 4c. THE A5 ARM — partial teardown

Run 2026-09-04 on the same disposable-host pattern. **11 passed, 0 failed, first
run.** A4 took six attempts; A5 took one, because the design question was settled
by measurement before any code was written.

A5 needed a lifecycle the engine did not have: `--recover` adopted the ENTIRE
ledger and released all of it, so there was no way to take one unit down.

**The hard part is the bridges, and it is a correctness question rather than a
plumbing one.** A bridge carrying a cross-unit link is declared by BOTH units —
that is what makes it the link. Measured on the micro fixture: **all 120 bridges
are shared between a pod and the core and NOT ONE is exclusive.** A partial
teardown that removed "its own" bridges would have cut the core's links to a pod
still running — with every container still up, and nothing looking wrong until
traffic was tried.

So `--release-unit LAB` releases only what is exclusive to that unit, derived from
R (the ledger records what we own; the topology records who uses it). An unknown
unit name REFUSES rather than falling back to releasing everything.

`Transaction.defer()` is the other half. `release_all`'s have-check exists to
catch durable ownership with no durable release, and a partial teardown leaves
entries unacted-on ON PURPOSE. The two must not look alike, or the check either
fails every partial release or stops catching what it was written for — so
out-of-scope entries are NAMED, not skipped, and stay owned for a later run.

### Measured

| stage | result |
|---|---|
| deploy | 50 of 50 planned containers running, 126 resources kept |
| release `c12-dc1-pod002` | **2 resources adopted, 124 left owned** — the whole design in one number |
| victim | 0 containers left, management network gone |
| **survivors** | `c12-core` 6/6 and `c12-dc1-pod001` 22/22 **byte-identical** — same Ids, same StartedAt, still running |
| bridges | all 120 survive; 60 dropped from 2 ports to 1 (exactly the 60 pod-2 was attached to); **none reached zero**, so no survivor was disconnected |
| ledger | 124 entries still owned, so the rest can be released later |
| final release | host empty: 0 containers, 0 lab bridges, 0 lab networks |

The assertion that matters is not "pod-2 is gone" — that is the mechanism. It is
that the survivors are the SAME OBJECTS. A survivor that was restarted, recreated
or quietly disconnected is collateral damage, and counting containers would have
missed all three.

## 4d. THE A6 ARM — the canary path holds

Run 2026-09-04. **14 passed, 0 failed.** Measured to ADR-3 §5's fixed service
level, which was written before any of this ran and was not adjusted to fit it.

A4 asked whether the machinery owns things correctly; A5 whether one unit can be
removed without disturbing the others' OBJECTS. A6 is the first arm that asks
whether the fabric **forwards** — containers can be byte-identical and a path
still be dead.

| clause of the service level | required | measured |
|---|---|---|
| one exact pod-1-spine ↔ core path across its dedicated bridge | — | `dc1-pod001-bk-p1-spine01:Ethernet0` (10.128.0.86) ↔ `dc1-ba-core001:Ethernet0` (10.128.0.87) |
| baseline before anything is destroyed | 20/20 | **20/20** |
| probe interval, window | 200 ms, from before the destroy until 10 s after | as specified |
| transmitted, loss | ≥50, **exactly zero** | **250 transmitted, 250 received, zero loss** |
| pod-1 and core manifests | unchanged | 6/6 and 22/22 byte-identical |
| bridges formerly shared by pod-2 and core | present and attached | all **60** present, every one still carrying the core's side |

The addresses come from R: `portmap.py` already allocates the /31 for every
interswitch link, so the canary configures the addresses the fabric would have
used rather than inventing a pair. The link is the first sorted pod-1-spine ↔
core link, so the choice is reproducible rather than whichever was handy.

### Two things had to be fixed, and both were in the instrument

**ZTP.** The `-ztp` image boots into ZTP discovery and stays there forever on a
host with no ZTP server. In that state `show interfaces status` is EMPTY — and I
read that as "the nodes have no data ports". **They have 32 the whole time**:
`Ethernet0`–`Ethernet124` are in the PORT table and present in the kernel. ZTP was
holding the configuration, not withholding the ports. `ztp disable` is a stock
SONiC operation and invents nothing. Hand-writing a PORT table would have been a
second derivation of the fabric's port map — the exact shape of the defect that
once applied a 32-port table to 64-port switches.

**A greedy backreference.** `sed 's/.*\([0-9]*\) received/'` matches as much as
it can first, so on `20 packets transmitted, 20 received` it captured the LAST
DIGIT — zero — and the gate refused a path that was passing 20/20 **while printing
the proof of that directly underneath itself**. Parsed by field position now, and
an unparsable result is `-1` rather than `0`: "could not read" is not "none
received".

### What A6 does NOT show

It is a canary, deliberately: **one link, not the pod's dataplane**, and the two
endpoints were configured by hand for the test rather than provisioned. There is
still **no per-unit configuration path** — stage 50 is written for the monolithic
`clab/gpufab.clab.yml` at a fixed path and cannot configure unit labs. What A6
proves is the property the unit-lab design puts at risk: destroying one unit does
not disturb a path crossing the shared tier.

## 4e. THE A7 ARM — the revision, and the gap it found

Run 2026-09-04. **10 passed, 1 failed** — and the one failure is the finding.

A7 could not be run as written, because **there was nothing to be RED.** The
executor's rc answers "did THIS OPERATION do what it said" — releasing one unit
returns 0 because the release worked, which is correct and is not a statement
about the fabric. Nothing anywhere answered *is the fabric complete?*, so a
partial fabric had no verdict at all. `unit_executor.py --verify` is now that
verdict: 0 GREEN, 1 RED, 2 COULD-NOT-MEASURE, **verified against the model, not
the ledger** — a check that consulted the ledger could only confirm its own
bookkeeping, and the interesting states are exactly the ones the ledger is happy
about.

| state | verdict |
|---|---|
| S0 nothing deployed | RED |
| S1 everything deployed and ready | GREEN |
| S3 a switch STOPPED but still present | **RED** — presence is not function |
| S4 that switch started again | GREEN |
| S2 one unit released | **RED**, while the release's own rc was 0 |
| S5 a management network removed by hand | **RED**, though the ledger still claims it |
| S6 everything released | RED |

Unmeasured is neither: run on a workstation with no docker it reports
COULD-NOT-MEASURE rather than guessing. "The fabric is broken" and "I could not
tell" send an operator to different places, and only one is safe to retry.

### THE GAP A7 FOUND, AND ITS FIX

A7's first run failed one state:

    VOID  bridge:br00afcaccddbd is PRESENT and already ledgered

The shared bridges that correctly survived the release are still OWNED, so a
fresh deploy met `(preflight, PRESENT, already-ledgered)` and refused. **A5 showed
a unit can be taken down; A7 showed it could not be put back** — the operation
the whole unit-lab design exists for. `--release-unit` had no inverse.

That cell is not weakened: it is what catches a stale ledger meeting a live run,
and it still refuses for every other caller. `--deploy-unit LAB` is the explicit
path, and it **BORROWS** rather than adopts.

**Borrowing is narrower than adopting: a borrowed resource is verified, attached
to, and NEVER RELEASED by this run.** It belongs to the units that are staying
up, so a rebuild that fails partway must not take the surviving unit's link down
with it — which is exactly what treating a borrow as an acquisition would do.
Five things must hold or it refuses: in the ledger, CONFIRMED created, PRESENT,
READY, and identity unchanged.

Measured on the disposable host, A7 now **14 passed, 0 failed**:

    rebuilding c12-dc1-pod002: 2 created, 60 borrowed from units that are staying up
    PASS  the released unit is back (22 containers)
    PASS  the bridge count is unchanged (120) — the shared ones were borrowed, not rebuilt
    PASS  the core is byte-identical across the rebuild
    PASS  the fabric is GREEN again once the unit is back

"2 created, 60 borrowed" is A5's finding restated from the other side: pod-2's
only exclusive resources are its network and its lab, because every one of its 60
bridges is shared with the core.

**The unit lifecycle is now closed**: deploy → release one → rebuild one →
release all, with the fabric verdict correct at every step.

S3/S4 were moved before the release so each differs from GREEN in exactly one
thing. The first version released a unit and then tried to REDEPLOY to get back to
whole; the redeploy VOIDed for the reason above, and the arm only NOTED its rc
instead of gating on it — so S4 was measured against a fabric that had never been
made whole. That is the defect this arm exists to catch, in the instrument again.

## 4f. THE CONFIGURATION PATH (points 1-6)

The gap §4e left open — "a unit lab boots but is not a fabric" — is closed. Six
points, each with a host-free contract before any wiring.

| # | what | where |
|---|---|---|
| 1 | `render_bundle(source, device_set)` extracted from the canonical renderer | `render_fabric_ztp.py`, t84 |
| 2 | each unit's exact device set and configuration digests, in R | `tools/unit_plan.py`, t86 |
| 3 | configuration applied after lab readiness, before `--keep` | `unit_executor.execute`, t83 |
| 4 | initial deploy configures every unit; `--deploy-unit` only its own | `tools/unit_configure.py`, t87 |
| 5 | configuration failure releases only new exclusives, preserves and revalidates borrows, leaves RED | t83 |
| 6 | host-free conformance, then the FRR fast path and a SONiC run | t84, `a8-acceptance.sh` |

**ALLOCATION BEFORE FILTERING is the property everything rests on.** A VTEP set,
a peer table and an address plan are properties of the whole fabric, so a renderer
handed a smaller source produces a smaller fabric's answers and every artifact
stays internally consistent. `render_bundle` derives the complete model and its
global feature allocation from EVERY device and only then filters what it emits —
and t84 asserts that projecting a unit out of the full render is BYTE-IDENTICAL
to rendering that unit directly.

`interim_deploy` is deliberately NOT the seam: it merges intent into live running
state, which is correct because an operator owns some of it, so making it pure
would create a second rendering authority.

**THE COMPARISON IS THE MANIFEST-OWNED PROJECTION** (t85), and both wrong
comparisons are killed by mutation. Compare everything and the push looks
permanently out of sync, because it legitimately inherits state the render has no
opinion about. Compare nothing and every switch is trivially in sync, so the push
skips all 48 and leaves a fabric at factory.

### The acceptance arm

`deploy/checks/a8-acceptance.sh` runs the cycle an operator actually performs.
**13 passed, 0 failed at frr fidelity:**

    deploy + configure   220s, 50 containers, 46 devices configured   GREEN
    release one unit     28 containers remain                          RED
    rebuild + configure  97s, 2 created / 60 borrowed, 20 configured   GREEN
                         survivors byte-identical (5 and 21 containers)
    release everything   host empty                                    RED

**20 against 46 is the assertion that matters.** A rebuild that also reconfigured
the core would write CORRECT configuration and report success; the only place it
shows is the count.

`fabric_model` had priced frr fidelity at 0.05 GB against 4.0 since it was
written and NOTHING READ IT — every switch was emitted as a sonic-vm whatever the
profile asked, so the cheap path was declared, costed and unreachable. Fidelity
now decides how a switch is RUN, not what it is: the model's kind is unchanged
(seed, interim_deploy and expected all key off it), and t77 asserts the two
fidelities emit the same devices and the same links. Otherwise the fast path
would be a different fabric that merely happens to be quicker.

### What this phase found

- **`deploy_host` hardcoded `clab-gpufab-{name}`** — the canonical pusher could
  not address a unit lab's containers at all.
- **`a4-host sync` shipped only one repo.** The configuration path renders from
  gpufab-network, so every unit plan failed with ModuleNotFoundError.
- **Authorship without identity could pass `--keep`** — reproduced as
  `acquire=True` with `confirmation=(True, None)`. Cleanable, not keepable.
- **Borrow checked identity only when recorded, and only before use.** Both
  closed: both sides must be measured, and borrows are re-measured after the work
  and after cleanup, non-mutating always.
- **My own mutation harness scored `"10 failed"` as SURVIVED**, because it
  matched the suffix `"0 failed"`. It had been doing that for most of the phase.

## 5. What the reviewers could NOT settle

Named here because an unexamined path is worth more written down than assumed
safe. All three were offline by construction (no host contact), so anything
resting on real containerlab or docker behaviour is unverified:

- **The real blast radius of `containerlab destroy -t <topo> --cleanup` on clab
  0.77** — whether it selects containers by the `containerlab=` label or by
  derived names, whether it removes the mgmt docker network and its `DOCKER-USER`
  iptables rules, whether it touches `kind: bridge` nodes, and exactly what
  `--cleanup` removes. This is the multiplier on the measure/mutate split.
- **clab 0.77's `prefix` and `mgmt.bridge` semantics.** Both are now refused
  outright rather than reasoned about.
- **Whether `docker network rm` on a network with foreign endpoints is refused by
  the daemon** in this docker version.
- **Whether c12's content-hash bridge names can collide with the live fabric's.**
  The names are un-namespaced hashes of the link. A collision fails closed at
  preflight, but it is the enabling condition for the recover path above.
- **Behaviour under real root/`sudo`, `/var/lock` permissions, and real `flock`
  semantics** on the host filesystem.

## 6. Open, and explicitly NOT done

- **A4, A5, A6 and A7 are DONE** (§4b–§4e). The whole one-host A-series is

- **The unit lifecycle is CLOSED** — deploy, release one, rebuild one, release

- **There is no per-unit CONFIGURATION path.** Stage 50 is written for the

## 7. If you change this code

The rule that produced the current state, and the reason it is worth the
friction: **express the invariant once, and make every new resource an instance
of it.** The predecessor's three identical defects were not three mistakes; they
were one mistake made three times because the rule lived in three places.

Concretely: do not add ownership logic to `c12-unit-labs.sh` or to any future
launcher. A launcher generates artifacts and calls the executor. If a new rule
seems to belong in the launcher, it belongs in `ownership.py`, and it needs a
hand-authored cell in `t81` before it needs an implementation.
