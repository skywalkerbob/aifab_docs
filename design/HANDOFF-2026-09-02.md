## 2. Stage 30 reported a partial seed as complete (FIXED)

`deploy/30-seed.sh` was two `seed.py` invocations under `set -e` and nothing
else, so "complete" meant "the interpreter returned 0". A run that wrote a
PARTIAL topology was therefore reported complete: `head.sh` logged *reached and
finished stage 30-seed* while NetBox held 21 of 124 devices. The fabric role
gates on that same number from that same derivation (`roles/fabric.sh:302`), so
it waited out its entire SoT timeout — 1810s — and the run died there, thirty
minutes and a whole role away from the stage that was actually wrong.

`seed.py`'s own "seed complete: N objects created this run" cannot close this. It
counts what the run DID, and the stage is deliberately idempotent, so it prints 0
for a correctly seeded SoT and 0 for a half-seeded one.

The stage now reads back what EXISTS — devices, cables, and devices lacking
`primary_ip4` — and compares against `tools/expected.py`. A readback that answers
nothing is UNVERIFIED and refuses; it is never read as a count of zero.

- `deploy/30-seed.sh` — the `seed_verify` block, bounded by extraction sentinels.
- `tests/t72-seed-completion.sh` — 17 assertions, host-free, phase `seed-completion`.

**Trap for the next reader.** The first version of t72 scored a mutant GREEN.
`set -- ${_seen:-0 0 0}` still refuses, so `rc=1` looked correct — but it refuses
by reporting "0 of 124 devices", fabricating a measurement of a NetBox that
answered nothing. Two assertions now require the refusal to say UNVERIFIED and to
NOT report silence as a measured zero. **Asserting the exit code was not enough;
the refusal REASON had to be asserted too.**

## 3. Every host sync was broken (FIXED)

`tools/sync_branch.sh` derived its destination from `basename
remote.origin.url`. `deploy/00-bootstrap.sh` clones into
`/opt/gpufab/gpufab-<role>` and holds that LOCAL name stable regardless of what
the remote is called. The two agreed only for as long as the remotes were also
named `gpufab-*`.

The GitOps rename to `aifab_*` therefore pointed every sync at
`/opt/gpufab/aifab_platform` — a path no host has. Both hosts refused with
"does not exist on <host> — seed the host first", blaming the host for a mapping
error on the workstation. Nothing was ever shipped anywhere wrong; the refusal
was correct. But no sync could succeed.

`_host_dir()` now derives the ROLE (tolerating both prefixes, so an older
checkout is not stranded) and rebuilds bootstrap's path. An unrecognised name
REFUSES with rc=2 and names `--dest`.

- `tools/sync_branch.sh` — the `dest_derivation` block, sentinel-bounded.
- `tests/t73-sync-dest.sh` — 11 assertions, phase `sync-dest`. **Case 5 is the
  load-bearing one**: it asserts `00-bootstrap` still clones into
  `/opt/gpufab/gpufab-$_r`, binding the two derivations so the agreement is
  checked rather than assumed by a comment.

## 4. The exporter claimed a deploy never happened (FIXED)

`monitoring/platform_health.py:netbox_devices()` returned 0 on any exception.
`platform_services.yaml` declares `30-seed: {kind: netbox_devices, min: 1}`, so
that number becomes a claim about a DEPLOY — and the head exporter published
`gpufab_platform_stage_ok{stage="30-seed"} 0`, *"the seed stage never ran"*,
against a SoT holding 124 devices that answered in 0.14s when asked again moments
later.

#129 had fixed the UNCONFIGURED half of exactly this and stopped there. The
docstring argued for leaving the rest: *"a genuinely unreachable-or-empty SoT
still returns a number."* Those are opposite facts and only one of them is
knowable from a request that failed. Measured against an unroutable address,
`netbox_devices()` returned 0 after exactly its 5s timeout.

A failed probe now answers `None`. **Returning `None` could not be the whole
fix**: `t04` scores stage artifacts by counting series that READ 0, so an absent
series scores clean — trading a wrong red for a silent green, which is the trade
the neighbouring `sot_known` comment already refuses. So the exporter also
publishes `gpufab_platform_sot_reachable`, and t04 asserts it.

The probe is cached per scrape so the artifact loop and that metric cannot
disagree, and `collect()` resets the cache so one transient failure does not
freeze into every later scrape.

- `tests/t74-sot-reachable.sh` — 7 assertions, phase `sot-reachable`. Case 4 is
  the one that matters: a SoT that ANSWERS and reports zero devices must still
  report the stage did not run, or the fix would have removed the finding it
  protects.

## 5b. Stage 00 could not survive a held dpkg lock (FIXED)

The first paired deploy died at `stage=00-bootstrap` with `rc=127`. Because that
is the FIRST stage, `containerlab destroy` never ran and the live fabric was
never touched.

`unattended-upgrades` held the dpkg lock for the full 600s deadline. That is a
condition stage 00 is written to handle — and its handler was dead code:

    ./00-bootstrap.sh: line 83: FAIL: command not found
    [FAIL] fabric BOOT phase failed (rc=127)

`00-bootstrap.sh` is a deliberate ONE-FILE seed that runs where `lib.sh` may not
exist, so it defines `FAIL_SEED` itself. `_wait_substrate` called bare `FAIL`,
which lives in `lib.sh` — the only bare `FAIL` in the file against six correct
`FAIL_SEED` calls. A legitimate environmental failure reported as a broken one,
with `rc=127` pointing at a missing binary rather than a held lock.

**DO NOT "REPAIR" THE lib.sh SOURCE GUARD.** It was `grep -q
'^GPUFAB=/opt/gpufab' ./lib.sh`, which has never matched (`lib.sh:14` is
`GPUFAB="${GPUFAB:-/opt/gpufab}"`). Nothing noticed because stage 00 needs no
symbol from lib.sh — verified by enumerating every name lib.sh defines and
grepping each against the file with comments stripped. **That accident was
protective**: `lib.sh:57` defaults `PROFILE` to the **s0-64** rung, so sourcing
it would make stage 00's refusal of an unset PROFILE unreachable and let a
512-GPU fabric build against a 64-GPU SoT. The dead source is now removed and the
reason recorded in the file.

### Why the lock was held for five hours

`needrestart`, running as a dpkg post-install trigger, issued ONE `systemctl
restart` covering nine units including `systemd-networkd`, `systemd-journald` and
`systemd-resolved`. systemd runs that as a single transaction and it wedged: five
hours elapsed for 31 seconds of CPU, no dpkg activity after the first minute.
Stopping `systemd-networkd-wait-online` released it immediately, with networkd
still active and all 124 clab nodes intact.

**The precise mechanism of the wedge is NOT established, and nothing here guesses
at one.** `wait-online` already carries a drop-in bounding it to `-i
ens4:degraded` and its own default timeout is 120s, so its logic alone does not
explain a five-hour hang.

What IS established is the hazard, which matters more than the hang: an
unattended background process restarting `systemd-networkd` and
`systemd-journald` underneath a running 124-node topology whose veths networkd
already tracks (130 links). Stage 00 now sets `$nrconf{restart} = 'l'` —
needrestart still LISTS what wants restarting, and restarts nothing. The setting
is read back from the file needrestart will parse, because a drop-in that
silently failed to land would leave the hazard in place while the stage logged
success.

- `tests/t75-bootstrap-standalone.sh` — 13 assertions, phase `bootstrap-seed`,
  7 mutants killed. It validates the needrestart drop-in with `perl`, because
  `restart = 'a'` also writes a syntactically valid file: any check short of
  parsing it and reading the value would pass while apt kept permission to
  restart networkd under the fabric.

## 7. Traps this session paid for

1. **Editing a script while an invocation of it is running.** Bash reads scripts
   incrementally. Rewriting `sync_branch.sh` mid-sync shifted byte offsets under
   the live interpreter, producing `line 160: syntax error` and leaving
   fabric-01 converged-but-unverified. Let host operations finish first.
2. **`| tail` swallows the exit code.** `sync_branch.sh ... | tail -12; rc=$?`
   captured `tail`'s status, reporting `rc=0` for a sync that had refused.
   Redirect to a file and read `$?` directly.
3. **`git status --porcelain` counts UNTRACKED files.** A host check reported
   "modified tracked: 1" when the only entry was `?? .gpufab-source`, the
   provenance stamp `sync_branch` writes. Use `git diff --stat` for tracked.
4. **`sync_branch` ships the working tree; it does not advance host git.** After
   a push, hosts show "commits behind origin/main". The advance is
   `fetch` → verify `origin/main^{commit}` resolves → `checkout --force -B main
   origin/main` → assert HEAD == target, which is what `_gpufab_advance_repo`
   in 00-bootstrap does. Running all of stage 00 on a live fabric host is far
   more collateral than the goal warrants.
5. **`grep -q` inside a pipe inverts a check under `set -o pipefail`.** `grep -q`
   exits on the FIRST match, SIGPIPEs the upstream `sed`, and the pipeline returns
   141 — so `if sed ... | grep -qE ...` takes the ELSE branch precisely when the
   pattern DOES match. A t75 assertion reported "stage 00 does not source lib.sh"
   about a file that sourced it on line 71. Use `grep -c`, which reads all input.
   Only a mutation run caught it.
6. **`deploy-results` runs regardless of `--only`.** It is in phase 0b, outside
   the `ONLY` gate, so every `--only` run also prints the §5 failure. Not a bug
   in the phase being measured.

## 8. Method note

Every fix in §2–§5b was mutation-tested: the test was run against deliberately
broken versions of the code and required to go RED. **22 mutants, 22 killed.**
This caught two defects that no amount of re-reading would have — the t72 laundering
in §2, and the pipefail-inverted assertion in §7.5, which was reporting the OPPOSITE
of the truth about a file it had read correctly.

Where a mutant was killed only by an extraction guard, a refined mutant was
written that left the guard intact so the kill came from the real assertions.
A kill that comes from the wrong assertion is not evidence.
